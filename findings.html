What to fix next

The structural problems left after the cleanup milestone and the complexity work, each with options and a rough size, so the owner can choose what to fix next.

In 60 seconds

  • 24 findings in five groups. Architecture, coupling, duplication, dead code and tooling. Each has evidence checked against main, why it matters, two or three fix options with a rough size, and its roadmap item if there is one. This page suggests a priority but decides nothing.
  • Methods are small now, classes are not. Every member is below cyclomatic complexity 10 (Complexity). That metric measures branches inside one member. It does not measure how many members a class has, and IsometricSlice still holds hundreds of methods and fields in one MonoBehaviour (snapshot in §03).
  • One finding is marked high, and one is done. F01 is IsometricSlice's size. F08, the rehearsals reaching private members by string name, was fixed first because it made every extraction riskier: now a rename fails to compile instead of failing in a player run.
  • Much of the menu duplication already has a plan. Cleanup steps G and H and the UI Toolkit migration cover the two menu stacks, the hosted windows and Settings. Those findings link the plan rather than decide it again.
  • Some fixes are small. Dead loaders, an unused component, a class that a script cuts out of a source file by counting braces, and a duplicated set of data types each take a day or less (size S).

F01 · IsometricSlice holds the whole world in one MonoBehaviour high

Why this priority: it is the largest production class in the game, the menu migration's lodge-list, deck-builder and map slices all start inside it, and most of what the rehearsals reach is on it.

Evidence.

  • 19 partial files in Game/EmberGrove/Assets/Runtime/Exploration: IsometricSlice.cs plus Audio, Circuit, CircuitUi, DeckBuilder, Hud, Learning, Lessons, Onboarding, Preferences, Presentation, Progress, Settings, Table, Title, Versus, Waybook, WaybookMenu and World.
  • One MonoBehaviour; its member counts are in the table above. The journal alone has a CircuitPage enum with one value per page and a back stack of pages.
  • It boots the scene, reads the Circuit sidecars and builds the CircuitDefinition (F14), and owns the circuit field (CircuitState) with ApplyCircuit, SaveCircuit and CaptureCircuitSave. It also walks the traveller, draws the HUD and every lodge window, and runs the deck builder, lessons, onboarding, the Versus table lobby and the hand-off to Settings.

Why it matters. The partial files name topics but enforce nothing: any of the 19 files can read and write any of its instance fields, so a deck-builder change can break the title page. Nothing in the class can be tested without the scene and a player run. The roadmap's later migration slices move the lodge lists, the deck builder, and the map, tasks, dialogue and onboarding, and each of those starts by untangling its screen from this class.

OptionSizeTrade-offs
Extract one screen per migration slice. Each slice moves its screen's state and rules into a plain C# model that the new view binds to. The roadmap already plans the deck builder as "its model, then a redesigned view".M per sliceFits work already planned. The class shrinks only as slices land, and the boot, world and save core stays.
Extract the non-UI core first. A plain class takes circuit, ApplyCircuit, SaveCircuit, CaptureCircuitSave and the duel commit (CommitFinishedCircuitDuel), and a separate loader takes the sidecars (F14). The MonoBehaviour keeps references to both.LThe save and duel path becomes testable in the fast portable suites. Rehearsals that reach the moved members must follow them; since F08 they reach them directly, so the compiler lists every call site.
Freeze it. Add no new partial files or fields, and build new features in new classes.SStops the growth. Removes nothing.

Progress on the second option. Step 1 has landed as CircuitProgress, a plain class that the portable Persistence suite also runs. It owns the adventure's state, definition and save store, applying a change with its save and rollback, the restore fallbacks, the write and the finished-duel rule. CaptureCircuitSave and the save gates stay on the slice on purpose: most of a save's fields belong to other topics, and the traveller's position comes from live transforms. Step 2 moved the sidecar reads into CircuitContentLoader and the definition rules into CircuitDefinitionBuilder (F14). What comes next is in the roadmap's next actions. The evidence above is from before these steps.

F03 · A full ExpeditionApp for every hosted screen, Settings included medium

Why this priority: every Settings or Versus visit builds a battle app and reloads the content pack. The migration's Settings slice is a natural moment to change this.

Evidence.

  • IsometricCombatBridge.Begin creates a "Hosted session" GameObject and adds an ExpeditionApp for every HostedSessionKind: CircuitDuel, FriendlyGame, Practice, Lesson, Versus and Settings. IsometricSlice.ShowWorldSettings opens Settings this way.

F04 · ExpeditionApp's screen is an implicit state machine medium

Why this priority: which screen is open is spread over ten flags written from eight files, and each new window adds a flag and a place in an if-chain.

Evidence.

  • Ten public booleans decide what ExpeditionView draws: Busy, Paused, Handoff, HelpOpen, FeedbackOpen, SettingsOpen, NetworkMenuOpen, DeckMenuOpen, WorldCardLibraryOpen and MoveHelpOpen. The view adds its own private confirmTurn, and the session's Kind is fixed before start.
  • Eight of ExpeditionApp's ten files write those flags, and ResetScreen clears all of them except Busy.
  • Hand-kept lists read them, and they differ. CanAct combines CanActMenusClosed (eight of the flags) with CanActGuidanceClear (WorldCardLibraryOpen, MoveHelpOpen and a lesson wait). UpdateRivalScreenOpen, which holds the rival back, checks eight flags too, but not the same eight: it leaves out NetworkMenuOpen and DeckMenuOpen.
  • ExpeditionView.Render picks the screen by the order of the checks in RenderFocusedWindow, RenderScreen and RenderWindow.

The screen choice in ExpeditionView.cs. "Focused" is true when any of WorldCardLibraryOpen, SettingsOpen, confirmTurn, FeedbackOpen, HelpOpen, Paused or MoveHelpOpen is set. Nothing stops two of them being true at once; the order of the checks decides.

Why it matters. Combinations that should be impossible, such as Paused and SettingsOpen together, can be represented, and only the order of the if-chain settles them. When a window is added, every reader must be updated by hand, and they already differ. The migration's input gate needs to know exactly which window is open.

F08 · Rehearsals and tools reach private members by string done

Done 2026-11-07, with the first option below: the rehearsals and tools now reach these members directly, so a rename or an extraction fails to compile instead of failing minutes later in a player run. That lowers the cost of F01, F02, F04 and F21.

What it was. About 1,060 accesses named a member in a string, about 850 of them through CircuitSliceChecks' helpers Get, Get<T>, Set, SetProperty and Invoke, mostly on the IsometricSlice instance. Pages opened through Enum.Parse on the private CircuitPage type, rehearsals wrote ExpeditionApp's compiler-generated backing fields such as <State>k__BackingField, the card presentation check found CurrentCardWorkshop by its type name, and Tools/ExpeditionNetworkChecks and Tools/ExpeditionPerformance/WorldFactChecks.cs read ExpeditionAuthority and the relay's internals by name.

What changed.

  • The about 220 members those accesses reach (fields, methods, properties, setters and nested types) are internal instead of private, or have an internal set, and the tests use them directly. Where a member already had a read accessor, the tests use that instead. The five helpers are gone. Where several fields shared one declaration, only the fields the tests use moved to a declaration of their own.
  • Pages, deck-builder sheets, input kinds and practice steps are enum constants such as CircuitPage.Deck, not strings compared with ToString().
  • The Card Workshop proof moved to Assets/Tests/Editor/CardWorkshopChecks.cs, which compiles into the editor assembly and so can call CurrentCardWorkshop. It registers itself with the runtime half at editor load.
  • The network rehearsal sets its short relay-readiness timing through public toolkit members: RelayReadinessPolicy, ExpeditionNetworkSession.RelayReadiness and a ListRelayRoomsAsync overload that takes a readiness handler and a policy, in the same way the session's constructor already takes a readiness handler. The toolkit's other internals stay closed to the game. Tools/ExpeditionRelay gives ExpeditionNetworkChecks InternalsVisibleTo, and WorldFactChecks compiles the toolkit source it reads.
  • In the shipping player, the game assembly's compiled code is unchanged except for two read-only accessors on DuelUi.MenuColour, which the palette check reads instead of its private fields. The networking assembly differs only by the public relay-readiness members above.

Still by name, on purpose. The palette check walks DuelUi.MenuColour's colour fields by the names in the palette role table, because that table is content that names roles as text, and the check exists to prove the two agree. IsometricSliceBuild still finds Unity's AndroidExternalToolsSettings by name, because that type exists only when Android support is installed; it throws a clear message if the API is missing.

The cost. internal is wider than private: any code in the same assembly can now use these members. Read an internal member on IsometricSlice, ExpeditionApp or ExpeditionView as "the rehearsals use this", not as an interface for other game code.

OptionSizeTrade-offs
Chosen. Make the members the rehearsals use internal and call them directly. For the .NET tools, internal is visible where a tool compiles the source itself; the relay project needs InternalsVisibleTo.MRenames become compile errors. Visibility widens inside the assembly, and the change is wide but mechanical.
Give each large class a narrow QA surface: one internal, QA-guarded accessor that exposes what the rehearsals need, and nothing else.M–LOne place lists every seam. More code to keep.
Keep the strings, and add a fast check that resolves every name the rehearsals use before a build is made.SA broken name shows in seconds rather than after a build. The coupling stays.

09How this page was measured

Everything here was read from git at main (ca8d41e, 2026-11-07), never from a working checkout, except F08's "What changed", which describes the code after that fix. Re-measure before relying on any number.

  • Member counts come from a Roslyn syntax parse (Microsoft.CodeAnalysis.CSharp 4.13) of every .cs file under Game/ and Toolkit/, with UNITY_EDITOR, CIRCUIT_QA and EMBERGROVE_QA defined so that QA code is included. Partial parts are summed by full type name. Methods include constructors and operators. Instance fields exclude const and static fields. Parsing with no defines drops the QA-only classes, removes one method and one field from IsometricSlice, and one method from ExpeditionView.
  • String-keyed reflection, counted on main before F08 was fixed, counts calls to Get, Set, SetProperty and Invoke (also written Rehearsal.Get and so on) whose member argument is a string literal, including the writes to <Name>k__BackingField fields, plus GetField, GetProperty, GetMethod and GetNestedType with such a literal, across Game/EmberGrove/Assets/Tests. The total of about 1,060 also counts enum names compared through ToString(), page names passed to Page("…") and Enum.Parse, the Card Workshop check's lookups, and the name lookups in Tools/ExpeditionNetworkChecks/Program.cs and Tools/ExpeditionPerformance/WorldFactChecks.cs. Each name was then looked up in the Runtime, Editor and Toolkit sources.
  • References, guards and callers were found with git grep on main and read in context. A "no caller" claim means git grep found no call site in the whole tracked tree, which includes the scene and prefab files.
  • Complexity is not measured here; Complexity owns it.
