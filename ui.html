UI & menus

How the two code-built uGUI menu stacks, the one UI Toolkit title page and the input routers fit together: who draws each screen, how a press reaches a focused control, and where the shared colour, type and spacing roles live.

In 60 seconds

  • Two menu stacks, one at a time. The lodge stack (IsometricSlice partials) draws the title, the field HUD, the journal windows, the task book and the deck builder. The hosted stack (ExpeditionView partials) draws the battle, pause, Versus and the full Settings screen. While a hosted session runs, the lodge stops reading input and hides its canvas (§02).
  • Almost everything is uGUI built in code through the static factory DuelUi, which also holds the one role table both stacks read: MenuColour, MenuType and MenuSpace (§04). The exception is the title menu, which is UXML and USS on a world-space UI Toolkit panel laid on the notebook (§05).
  • Screens are thrown away and rebuilt. ExpeditionView.Render() and IsometricSlice.DrawModal() destroy the old GameObjects and build new ones. Focus and scroll position survive by name, so GameObject names are load-bearing (§03).
  • Each stack has one input router, and Unity's own navigation is off. The hosted router is UpdateShellInput, the lodge router is UpdateFrameInput → NavigateModal. Both use MenuNavigationRows to work out which control is above, below or beside the focused one (§06, §07).
  • Much of it is still written twice: two routers, two device enums, two focus painters, three glyph prefix mappings, two entrance motions. The planned move to UI Toolkit is in the roadmap (§12).

Before you start

  • Know uGUI's EventSystem, Selectable and ScrollRect, and the Input System's Keyboard.current / Gamepad.current device API. This page does not explain them.
  • Read Hosted Sessions first if you do not know how a duel, practice, Versus or Settings visit becomes an ExpeditionApp. This page covers only what that session draws and how it reads input.
  • The player-facing rules (the one Back rule, every binding, what each setting does) are owned by PLAYER_CONTROLS. The art-facing rules (menu roles, the dim, art slots) are owned by CIRCUIT_PRESENTATION. This page links them and does not repeat them.
  • Paths in the tables are under Game/EmberGrove/Assets/ unless they start with Toolkit/.

How the hand-off keeps one router live

  1. Lodge code calls IsometricCombatBridge.Play. While it runs, inEncounter is true, so IsometricSlice.Update runs UpdateFrameEncounter in place of the world and its input. That method can cancel a session that is still loading and commits a finished duel. It also hides the lodge canvas as soon as the hosted view exists.
  2. Begin creates a "Hosted session" GameObject with an ExpeditionApp. Its Start loads the content pack, then adds ExpeditionView and calls Initialize. That builds the "Expedition canvas" (sorting order 100) and adds an EventSystem with InputSystemUIInputModule only if the scene has none.
  3. Play first records a RuntimePreferences snapshot: quality, frame rate, audio volume, cursor, the EventSystem's sendNavigationEvents and its selection. It restores the snapshot when the session ends.
  4. ExpeditionApp.FinishSession disables the app and the view before it calls back. Play then waits one more frame after releasing, so the press that finished the session cannot also act in the lodge.

The six session kinds and the bridge are on sessions.html §02, and the full session lifecycle is on the rest of that page.

03How a screen is built

Neither stack updates a screen in place. A redraw destroys the old GameObjects and builds a new set from the current state. Only a few long-lived layers survive. Focus, scroll offsets and the page history are carried across the rebuild by name.

Render() in ExpeditionView.cs. Every hosted screen goes through this order. SettleControlTints, RefreshTableInput and BuildBattleGuidance run after FinalizeShell. Which screen and window RenderScreen and RenderWindow pick is set out on sessions.html §06.

  • What survives a render: the backdrop ("Persistent expedition environment"), the single "Stable menu scrim", the "Navigation hint dock" (§08) and the "Independent notifications" layer that shows app.Notice.
  • Windows are shells around an input shield. Modal, PortraitPanel, WorldPanel and ConnectionPanel each make a full-screen DuelUi.Button whose name ends in "shield". It has the clear colour ShieldBlocksInput, and the panel sits inside it. The shield blocks clicks to whatever is behind it. RefreshModalPresentation then hides every shield except the top one and puts one scrim under it. The rule for why only one dim is drawn is in The dim behind an open menu.
  • Two passes edit after building. SkinWaybook repaints window panels and buttons by role. RewriteHostedMenuCopy then finds buttons and labels by GameObject name and replaces their text, so the words a player reads are not always the words the builder wrote.

Lodge: IsometricSlice.DrawModal()

DrawModal calls DrawCircuitModal, then ApplyWorldPreferenceText (text size and High Contrast), then RebuildModalNavigation. DrawCircuitModal sends the title and the club opening to their own surfaces. For every other page it hides the written title, keeps the "Circuit shade" and "Travel journal" shell while a window stays open, and destroys and redraws the page content. The page is chosen by a switch on circuitPage, split over DrawCircuitModalPage, DrawCircuitModalStoryPage, DrawCircuitModalCardsPage and DrawCircuitModalChoicePage.

Page history is a list. ShowCircuit pushes a CircuitPageState onto circuitBackStack. The state holds the page, the focused button's name, and the builder, lesson and map state. The list is capped at 16 entries and never drops the first. BackCircuitPage pops an entry and RestoreCircuitPage redraws it. The journal's pages themselves are described on world.html §06. The field HUD is separate: UpdateFrameLayout calls BuildHud, which rebuilds the whole lodge canvas whenever the screen size or safe area changes.

Names are load-bearing in both stacks. A rename compiles and then fails at run time. These names are relied on:
  • The "shield" suffix (TopNavigationRoot, RefreshModalPresentation, ApplyWorldMenuPresentationPanels).
  • The caption child "Label" (ApplyThemeText, SkinWaybookButtonCaptions).
  • The "Setting " row prefix (the focus highlight target).
  • Control names such as "Hand card id", "Unit id", "Cancel leave" and "Settings tab n" (first-focus rules, §07).
  • Every name RewriteHostedMenuCopy rewrites.
  • The six title entry names (§05).
The rehearsals also find controls by name (QA & Rehearsals).

04DuelUi: the factory, roles and palettes

DuelUi is an internal static class in namespace EmberGrove. Both stacks build their uGUI controls through it, and both read their colours, type sizes and spacing from the three role tables nested inside it. A content pack can change some of those colours through a palette, and High Contrast overrides any palette.

MemberWhat it makes
RectA RectTransform anchored top-left, with x, y, width and height in the caller's units (y measured downward)
Box, ArtAn Image: Box is rounded and sliced by default, Art is unrounded and shows a given sprite. Neither takes raycasts
LabelA TextMeshProUGUI using the default TMP font, with ellipsis overflow and no raycast
ButtonA Box plus UnityEngine.UI.Button and a centred child label named "Label". Its navigation is Navigation.Mode.None, because the routers move focus themselves (§06)
Border, ShadowAdd a DuelUiInsetBorder (a continuous stroke inside the control, kept sharp at fractional scale) or a drop shadow of MenuSpace.ShadowDrop
Rounded, Glow, Ring, Shard, Hexagon; Light, EtchedSigilProcedural sprites, each generated once into a texture; and two decorations drawn from them
DuelPointerA component for pointer enter, exit and right-click, used by the hosted card and terrain hovers

The three role tables

  • MenuColour holds the theme defaults (DefaultAccent … DefaultPanel), their High Contrast counterparts, the control fills (ControlRest, ControlActive, ControlPressed, ControlDisabled), the surfaces (Line, Edge, Rule, Page, Inset), the waybook marks, and the scrims and shades with their alpha limits.
  • MenuType holds one font size per job. Most come in Landscape and Portrait forms for the hosted compositions, and some in a Short form for the ultrawide settings sheet. Circuit* sizes are for the lodge journal and Hud* sizes for the field HUD.
  • MenuSpace holds the insets, gaps and heights, under the prefixes Exp* (hosted windows), Journal* (the lodge journal) and Hud* (the field HUD), plus a few shared measures such as FocusRing, EdgeWidth and ShadowDrop, and the SettingsWide* measures.

Each value is in the units of the surface that draws it, so the same job can have different numbers in the two stacks. The rules for choosing and adding a role are in Menu roles: take an existing role instead of writing a number, and use IL comparison to prove that moving a site onto a role changed nothing.

How a palette and High Contrast reach a control

  1. A content pack's media.json may name a palette (MediaThemeDefinition.MenuPalette picks one of MenuPalettes). The format is in the pack contract.
  2. Each stack calls DuelUi.MenuColour.Use(SelectedMenuPalette) as its pack loads. The hosted stack does this in ExpeditionView.ApplyExternalTheme, the lodge in the ContentPackFiles.Load callback in IsometricSlice.Circuit.
  3. Resolve resets every writable role to the literal captured at start-up. Then, unless High Contrast is on, it writes the palette's colours over them, keeping each role's own alpha. The writable roles are exactly the names in the toolkit's MenuPaletteDefinition.MenuRoles. Slot throws for a name the table lacks, so a role the toolkit adds without a matching field fails the first time the table is used.
  4. MenuColour.UseHighContrast is called from ExpeditionApp.ApplyRuntimePreferences, which both stacks call when settings apply. The lodge also calls it at the top of BuildHud, because a hosted session may have changed the shared flag.
  5. Most controls read the roles when they are built, so a menu already on screen keeps most of its colours until its next redraw. The exception is the lodge's TravellerButtonMotion, which reads the control fills again every frame.

The five theme colours (Accent, Growth, Paper, Quiet, Panel) take separate routes. The hosted view copies them from the pack into a runtime copy of ExpeditionTheme in ApplyExternalTheme, and reads Theme.Accent and the others through its bronze, green, paper and quiet getters. The lodge reads them straight from the pack through Packed(...) in its ink, ivory, muted and accent getters, falling back to MenuColour.Default*. Both swap in the *HighContrast roles when High Contrast is on. The two stacks read High Contrast from different objects: the hosted view from app.Settings.HighContrast, the lodge from WorldHighContrast.

Colour roles on buttons

In the hosted stack, a button's colour job is the HostedMenuRole enum (Control, Chosen, Danger, Primary, Card, Back), stored on its ExpeditionFocusMotion. Builders set it with AsPrimary, AsDanger, AsChosen, AsCard or HeaderBack. SkinWaybookButton later paints the resting fill from that role, never from the button's name. The lodge's AsPrimary rests a button on CircuitPrimaryRest through TravellerButtonMotion.SetRestColor. Both stacks mix their main-action rest from the panel ground and MenuColour.WaybookMark, so the two match.

Art slots

The named art roles a pack may fill are listed once, in the toolkit's WaybookPresentationDefinition.ArtRoles. Only the lodge stack draws them, all through IsometricSlice.DrawWaybookArt(parent, role, …) in .Waybook. If the pack binds media to the role, it draws a RawImage at the slot's authored opacity and returns true; otherwise it returns false and the caller draws its procedural fallback. The callers are the journal frame and page and the dialogue panel and portrait (.CircuitUi), the task notes, packets, tape, stamps, route marks, task picture and mascot (.Waybook), and the club opening page (.Onboarding). The hosted stack's book frame is TravellerWaybookFrame, a mesh drawn in code that reads no slot. The contract for artists is in Shared menu art target and the menu art replacement contract.

05The written title in UI Toolkit

The title menu is written on one leaf of the lodge notebook by a world-space UI Toolkit panel. A UIDocument is parented to the page surface of the authored LodgeWaybook prefab. The UXML owns the page's structure, the USS owns ink, type and state, and C# binds only what changes at run time. It is the only title: if the page cannot be built, the player sees a startup error naming the fault, not a fallback menu.

  1. DrawCircuitTitle calls DrawWaybookTitle. ResolveLodgeWaybook reads IsometricSectorVisuals.LodgeWaybook and runs LodgeWaybookBinding.Validate().
  2. EnsureWaybookPanelAssets loads UI/WaybookPage twice from Resources, once as a StyleSheet and once as a VisualTreeAsset. It also loads UI/WaybookPanel, a PanelSettings asset with the theme BloomfireTheme.tss and the text settings WaybookPanelText.asset.
  3. EnsureWaybookPanelDocument uses a UIDocument under the binding if there is one. Otherwise it creates a runtime host named "Lodge waybook page", which is what happens on main: neither the prefab nor CircuitJourney.unity carries a UIDocument. The host is parented to PageSurface with worldSpaceSizeMode = Dynamic. EnsureWaybookInput adds a PanelInputConfiguration whose only event camera is the world camera, because the scene tags no Main Camera.
  4. The tree is instantiated and Q("Waybook page") is added to the root at a width of 620 page units (WaybookPageUnits), with its height taken from PageSize. The state classes are toggled, the heading is written and the six entries are bound from OrdinaryTitleChoices() in .Title.
  5. RestoreWaybookFocus refocuses the remembered entry. It does nothing in pointer mode. Then FitWaybookPanelToPage scales the host so the panel's mesh width equals PageSize.x. The fit retries every 16 ms, up to 90 tries, until the panel has a mesh.

If any step fails, it records the reason in waybookFailure, and DrawCircuitTitle calls DrawStartupError with that reason and a Quit button that a keyboard or controller can reach. Every other journal page, and CloseModal, calls HideWaybookTitle, so the page never stays in the world behind another window.

06The input routers

Pointer and touch presses on a control go through Unity's EventSystem and InputSystemUIInputModule as usual. Everything else (moving focus, Submit, Back, Start, shoulders, scrolling) is read straight from the Input System devices once a frame, by one router per stack. Both routers set EventSystem.sendNavigationEvents = false, and DuelUi builds buttons with Navigation.Mode.None. Unity therefore never moves focus or submits on its own, and a press is handled once.

One press through the hosted router, in ExpeditionView.Navigation.cs. Pointer presses take the left branch. The router only notes that the pointer is now in use, which hides the focus ring.

  1. Refresh. UpdateShellInputRefresh switches Unity navigation off again. If the top shield has changed, it saves the current focus and calls RefreshNavigation. If a control became available without a rebuild, for example when audio finishes loading, it updates the focus list and links.
  2. Device. A mouse click or touch press sets NavigationDevice.Pointer. Moving the mouse or turning the wheel does not change the mode. A controller press, the left stick or d-pad past .55, or the right stick past .5 sets Controller; if a text field is being typed into, that press leaves the field first. A navigation key sets Keyboard. Any keyboard or controller action hides the hover preview, and switching to either reveals the focused control.
  3. Command. UpdateShellInputCommands handles at most one command, in this order: Back (East or Esc), Start, the battle lock (while the player cannot act, nothing else is read), typing in a text field (only Tab acts), shoulders (and Q, E, Page Up and Page Down in the card library), then North or I (inspect, or erase on the on-screen keyboard), West, Tab, and Submit.
  4. Direction. With no command, arrows and WASD are combined as one logical direction (keys for the same direction count once, opposite keys cancel), or the d-pad and left stick are read. ResolveNavigationDirection ignores input under .3, needs .55 to start a new direction, and keeps a held direction while the stick stays near it. UpdateShellInputStep moves at once, repeats after .32 s, then every .12 s (every .04 s for a slider moving sideways). After a screen change, the direction must return to neutral before it moves again.
  5. Scroll. The right stick and Page Up / Page Down scroll the active ScrollRect directly.

Back runs a chain before it leaves anything. HandleShellBack closes, innermost first: move help, the controller keyboard, a card inspection, a drag, a display trial, an armed settings reset, Settings, the relay room pages, the end-turn question, a leave question, the pause's More. BackNavigation then clears an armed concede, and only after that does app.Back() run. The player-facing rule is the one Back rule, and the bindings are in Keyboard and controller. The router's many small UpdateShellInput* methods come from the complexity work; see Complexity.

The lodge router in IsometricSlice.cs and IsometricSlice.Hud.cs. It is a second, separate router with the same overall shape. The whole of IsometricSlice.Update, including the lobby, encounter and startup-error branches, is on world.html §03.

  • Nothing is read on the frame a window opened or closed (modalFrame), or for .12 s after one closed or the app regained focus (blockedUntil).
  • NavigateModalMove ignores small stick input and snaps the rest to one axis. It moves at once, repeats after .30 s, then every .13 s. Tab and Shift+Tab step through modalButtons. Submit (South, Enter or Space) invokes the selected button only if it is in that list.

  • In the world, arrows and WASD (or the stick and d-pad) walk the traveller. WASD stop being read while a letter board is open.

07Focus: scope, rows, memory and the ring

Focus is uGUI selection: EventSystem.currentSelectedGameObject. The routers decide what may be focused, what is next in each direction, where focus starts and returns, and how it looks. The written title is the exception: its focus is UI Toolkit focus, read through the panel's focusController.

Scope and screen keys (hosted)

TopNavigationRoot picks the last active child of the page whose name ends in "shield". During Play my turn it picks the "Turn help" strip instead. Controls outside that root are not in focusOrder. NavigationScreenKey names the current screen, and focus memory and first focus are keyed by that name:

MenuNavigationRows.Rebuild measures each control's own rectangle (decoration is ignored), sorts top to bottom and then left to right, and groups controls into one row when their centres differ by less than 35% of the smaller height. The hosted router passes IsHeaderBack as the heading test, so there a window's Back always gets a row of its own at the top; the lodge passes no heading test. With a group function, as the deck builder passes through BuilderNavigationGroup, controls in different groups never share a row: Up and Down stay in the group, and Left or Right at its edge crosses to the nearest row of the next group. Disabled controls keep their row, and Available is checked when a move happens. A vertical move keeps the column the player came from (preserveColumn).

The routers also write explicit selectOnUp / selectOnDown / selectOnLeft / selectOnRight links onto each control (RefreshNavigationLinks, RefreshModalNavigationLinks). Because Unity's navigation events are off, those links only record what the router computed. The router moves focus itself.

Where focus starts and returns

  • Hosted. rememberedFocus[screen key] stores a SemanticPath: the control's name path from the root, with a duplicate index for repeated names, and a "world-table:" prefix for controls on the 3D table. RefreshNavigation starts from the remembered path, then lets these rules change it, in this order:
    • the context rules: a window's Back is not restored after the screen changes, and the leave and retire questions start on their Cancel;
    • in battle, a legal destination after choosing a card (FirstActionTarget), or the source card again after cancelling;
    • a requested settings focus;
    • practice focus.
    If nothing has been chosen by then, InitialNavigationFocus picks by screen key, and failing that the first control that is not Back.
  • Lodge. A redraw of the same page keeps the selected button's name. A new page starts on the first control after the heading, then per-page rules override it by name (DrawCircuitModalFocus: builder, Your decks, episode, map, reward and replace, tasks). Going back restores the name saved in CircuitPageState.Focus.
  • Reveal before submit. If scrolling has left the focused control outside its viewport, the first Submit scrolls it back into view and does nothing else (ExpeditionFocusMotion.RevealBeforeSubmit). The lodge and the title page have their own versions for returning from pointer use.

How focus looks

The two stacks paint focus with separate components that read the same roles. In the hosted stack, RefreshNavigationMotion adds an ExpeditionFocusMotion to every focusable control. It draws a "Focus surface" fill of ControlActive and an ExpeditionFocusOutline ring MenuSpace.FocusRing wide in the accent colour, or an ink ring on a light fill. Cards and board units get a two-tone frame instead, and units on the 3D table get corner brackets. With a keyboard or controller the emphasis follows the selection; with a pointer it follows hover instead (ShowFocus). It also scrolls a focused control into view (Reveal). In the lodge stack, TravellerButtonMotion eases the fill from the resting colour to ControlActive, widens its DuelUiInsetBorder from 1 to FocusRing, and shrinks the button slightly while pressed. The player-facing description is in PLAYER_CONTROLS.

08Controller glyphs and hints

Hints are presentation only. As the comment in ExpeditionView.Glyphs.cs says, actual bindings stay with the router, so changing a binding means changing the router and every hint that names it. One function picks the controller family, but each of the three hint surfaces turns that family into sprite names itself.

ExpeditionView.ResolveControllerGlyphFamily(layout, product, manufacturer) joins the three strings and searches them. "dualshock", "dualsense", "playstation" or "sony" gives Sony; "switch", "nintendo", "joycon" or "joy-con" gives Nintendo; anything else gives Xbox. FaceGlyphLabel gives the printed name of a face or shoulder button for a family, used when no sprite exists. Sprites load from Resources/InputGlyphs/<prefix><control>, with the prefix xbox_, sony_ or switch_, plus shared dpad, key_enter, key_esc and key_updown.

10Settings screens

There are two settings screens. The lodge's CircuitPage.Controls page (DrawCircuitControls) holds camera follow, reduced motion, zoom, a movement guide and a "Game settings" button. The full Settings screen is hosted only: ExpeditionView.SettingsScreen, with the tabs Sound, Screen, Reading and Controls. The lodge reaches it by starting a hosted session of kind Settings.

  • Rows. SettingToggle, SettingChoice and SettingSlider build each row as a "Setting title" parent holding its title, help and value control. SettingLabel swaps in the words a player reads, while the object names stay fixed for navigation and saved focus. Left and Right change a choice through ExpeditionSettingAdjustment, or move a slider by one percent. A slider is an ExpeditionSettingsSlider, which separates touch adjustment from page scrolling. Trying a new window mode or resolution opens a trial with a countdown (DisplayConfirmation), and Reset asks once before it resets.
  • Navigation. Settings does not use MenuNavigationRows. It has its own explicit lists (§07) and its own shoulder handling: LB and RB change tab through ChangeSettingsTab, which can carry focus to the remembered row of the new tab.
  • Storage. Rows edit app.Settings through ExpeditionApp.ChangeSettings, which applies the change at once and saves to disk after input settles. The format, the keys and the save timing are on saves.html §08.

From the battle pause, and from Versus home, Settings opens inside the session already running (ExpeditionApp.OpenSettings). From the title or the Controls page it is a separate hosted session:

The planned move to UI Toolkit

Today the title page is the only UI Toolkit surface. It uses a UIDocument with its own world-space PanelSettings, and every other menu is code-built uGUI through DuelUi. The direction, the proof work, the order of the slices and the rule for stopping are all in Menus on UI Toolkit. Update this page as each slice lands. Until then, treat everything above as the current structure.
