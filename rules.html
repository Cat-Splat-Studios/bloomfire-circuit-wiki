How the rules decide

The CardForge rules layer: the result type, the combat reducer, the Circuit adventure rules, the retired progression shell and grid navigation, and how the game calls each of them.

In 60 seconds

  • The rules are plain C# with no Unity. The five rules assemblies under Toolkit/Packages/com.catsplat.cardforge/Runtime set noEngineReferences. They take values in and give values out. The game owns the live state, the saves and everything on screen. §01
  • Result<T> carries rule rejections. A failure holds a RuleError with a Code and a player-facing Message. Bind stops at the first failure. Match setup and catalog building throw instead. §02
  • Combat is one reducer. CombatRules.Resolve(state, command, catalog) validates the command, runs it on a deep copy and returns the new CombatState plus ordered CombatEvents. The local player, the AI and the network host all call it. §05
  • The Circuit adventure is a second reducer. Every CircuitRules transition returns Result<CircuitState>. On the game side, IsometricSlice.ApplyCircuit swaps in the new state and saves it. Duels carry a receipt, so a result can be applied only once, however many places report it. §09, §10
  • Most of Progression is retired. The game still uses ContentPack, its encounters and deck presets. RunRules, ProfileRules, StoryRules and CampaignRules have no game callers; only the toolkit sample and some check suites still use them. §07

Before you start

Read the Codebase Tour for how the game and the toolkit fit together. The toolkit's own package boundary table and the product names section explain why some namespaces say EmberGrove and others say CardForge. This page describes structure only. The match rules themselves are in GAME_RULES.md, and the adventure rules are in the Circuit module guide.

02Result<T> and RuleError

Runtime/Functional/Result.cs is one small file with two types. RuleError is a sealed class holding a Code (for checks and logs) and a Message (for the player). Result<T> is a readonly struct that holds either a value or a RuleError.

MemberWhat it does
Ok(value), Fail(code, message), Fail(error)The only constructors.
IsSuccess, Value, ErrorValue on a failure throws InvalidOperationException. Error on a default-constructed result returns an "uninitialized" error instead of null.
Map(f)Transforms a success. It does not run on a failure.
Bind(f)Chains another step that can fail and stops at the first failure.
Match(ok, fail)Runs one of two handlers. The game does not call it; it tests IsSuccess directly.

The combat entry points show the whole pattern in two lines (CombatRules.cs):

public static Result<CombatCommand> Validate(CombatState state, CombatCommand command, Catalog catalog) =>
    ValidateTurn(state, command, catalog).Bind(c => ValidateOwnership(state, c)).Bind(c => ValidateAction(state, c, catalog));

public static Result<CombatResolution> Resolve(CombatState before, CombatCommand command, Catalog catalog) =>
    Validate(before, command, catalog).Bind(valid => Simulate(before, valid, catalog));

Who returns Result<T>: CombatRules.Validate and Resolve; LessonRules.Prepare and Command; every CircuitRules transition, plus NewProfile, Validate, ValidateDefinition, Recover and PreviewDistrict; LandmarkRules.Complete; and ExpeditionAuthority.Receive on the network side.

There are three result types, not one. Progression does not reference Functional. Its RunResult<T> (in ExpeditionRun.cs) and WorldResult<T> (in WorldProfile.cs) have the same Map/Bind shape but a plain string error, and the three types do not convert into each other.

The reasoning behind the type and its limits (delegates can allocate, so hot query loops stay direct) is in Functional composition and the small monad. FUNCTIONAL.md covers the "functional core, imperative application" split and the runnable samples.

03Core data: definitions, catalog and match state

Every combat data type is in Runtime/Core/CombatContracts.cs. Authored definitions are copied into a Catalog, and a match is one CombatState value. Cards in a match are entries in a list, identified by their index, not by Unity objects.

TypeKindRole
CardDefinition, EffectDefinitionserializable classesThe authored card: Id, Title, Rules, Kind, Cost/Attack/Health, Ranged, Target and an Effects array of data rows (trigger, operation, selector, amount, terrain, condition). Both have Copy().
Catalogsealed classCopies the definitions, runs CombatRules.ValidateDefinitions and throws ArgumentException if any fail. After that it is a read-only lookup: Get(id), the indexer and Contains. Later edits to the source objects cannot change a running catalog.
DeckEntry, CombatConfigstruct, classA deck slot (definition ID plus upgrade level). CombatConfig holds the match numbers and the opt-in draw rules (OpeningHandSize, EmptyDrawDamage, SpentCardsStayDiscarded). Packs supply theirs as ContentPack.MatchRules.
CombatStatesealed classThe whole match: Players (two SideStates), Cards (a List<CardState>), Terrain per lane, Config, ActivePlayer, Turn, Round, Winner and RngState. Winner is −1 while play goes on, 0 or 1 for a winner, and 2 for a draw. DeepCopy() copies everything mutable.
SideStatesealed classOne player's life, shield, Pulse and per-turn counters, plus Deck, Hand and Discard as lists of card instance IDs.
CardStatestructOne card instance: Id (its index in CombatState.Cards), Owner, DefinitionId, Zone, Lane, Rank, Health, Shield, Ready, UpgradeLevel.
CombatCommandreadonly structOne action: Kind (Play, Attack, Move, EndTurn, Concede), Player, SourceId, TargetId, Lane, Rank. It has factory methods for each kind. A hero target is the negative handle from HeroTarget(player); HeroPlayer(target) reverses it.
CombatEvent, CombatResolutionsealed classesAn event is one thing that happened (Draw, Play, Damage, Death, Terrain, Bloomfire, Turn, Victory and more) with its text and handles. A resolution is the new state plus the read-only event list.
Why the state is mutable if the rules are "functional"

The snapshot types use public fields and mutable lists for compact, predictable storage. Immutability is an ownership rule, not a language guarantee: Resolve works on before.DeepCopy() and returns a different object. The caller keeps the old one, for example to animate from it. Code that edits a live snapshot behind the renderer or the AI breaks this. The toolkit states the rule in ARCHITECTURE.md, Runtime flow, and the data layout is explained in Data layout and measured optimization.

04CombatRules: the reducer

CombatRules (Runtime/Core/CombatRules.cs) is a static class. Its doc comment calls it the "deterministic functional boundary": every accepted action resolves on one owned snapshot. It also owns the match-deck rule that packs, Circuit decks and the game share.

Entry pointReturnsNotes
NewMatch(catalog, deck0, deck1, seed, config, …lives)CombatStateValidates the config and both decks, builds and shuffles both decks, then runs the first BeginTurn. Invalid input throws ArgumentException; it does not return a Result. A zero seed is replaced with a fixed constant.
LegalCommands(state, catalog)List<CombatCommand>Every legal action for the active player, in a stable order, ending with EndTurn. Concede is never listed. Empty once the match is over. The order is observable: it settles AI ties.
Validate(state, command, catalog)Result<CombatCommand>Three checks joined with Bind: ValidateTurn (match running, player, kind, whose turn), ValidateOwnership (the card is yours and in the right zone), ValidateAction (Pulse, placement, target, readiness, lane defence). Error codes include wrong-turn, not-owner, pulse, occupied-cell and lane-defense.
Resolve(before, command, catalog)Result<CombatResolution>Validate, then Simulate on a deep copy. A chain of more than 1024 queued effect operations fails as effect-limit instead of returning a partial state.
ValidateConfig, ValidateDeck, ValidateDefinitions, ValidateSnapshotList<string>Boundary checks. Catalog calls ValidateDefinitions. FairMatchSetup.CreateFairMatch calls ValidateSnapshot after its opening bonuses.
MaximumCopies, LegacyDeckSize, StandardDeckSize, IsMatchDeckSize, LegalMatchDeckconstants, boolThe one match-deck rule. Used by ContentPack.Validate, CircuitRules, FairMatchSetup, the session-deck check in PrepareTable and the game's rival-deck check in CircuitDefinitionBuilder.CheckRivals. The deck screens read MaximumCopies.
UnitAt, HandLimit, Units, AttackValue, MaxHealth, Cost, SpellAmountqueriesRead-only helpers for the view and the AI, so a stat such as attack or cost is worked out in one place.

The work happens in a private nested class, CombatRules.Simulation. Apply(command) pays the Pulse and runs Play, Move, Attack, EndTurn or Concede. Card effects are queued as PendingEffect values and run by Drain() in authored order, with CleanupDeaths() after each one. Death queues the OnDeath effects. BeginTurn and EndTurn handle Pulse, readiness, drawing and the end of a round. CheckVictory() sets Winner. Randomness is an xorshift step on CombatState.RngState, so the same state, command and catalog always give the same result. A small internal struct, BoardOccupancy (BoardOccupancy.cs), packs the twelve board cells into a bit mask for repeated placement queries; it is never stored on a snapshot.

The private helpers are named after the public method they serve: ValidateSnapshotSide, LegalCommandsMoves, NewMatchDealSide. The complexity pass introduced that naming when it split these methods with no change in behaviour (commit "Bring the CardForge core rules under complexity 10"); see Complexity.

To add a mechanic, follow AUTHORING.md, Add a new mechanic and Adding a reusable feature. A new card that uses existing effect rows needs no code.

05One accepted command

This is the path one player action takes in a local hosted match: from the view, through the reducer, back to the animation. The screen guard ExpeditionApp.CanAct blocks input while a menu or animation is open or the turn is not yours. It is not the legality check. That is the reducer's own Validate, which runs even if the guard is bypassed.

sequenceDiagram
  autonumber
  participant V as ExpeditionView
  participant A as ExpeditionApp
  participant R as CombatRules
  participant S as CombatRules.Simulation
  V->>A: SelectSlot / SelectLane / SelectHero / EndTurn / drag release
  A->>A: Submit(command), usually a SelectionCommands entry
  Note over A: guard: CanAct, command.Player == Viewer, PracticeAllows
  A->>A: ResolveLocal(command) when not Networked
  A->>R: Resolve(State, command, Catalog)
  R->>R: Validate: ValidateTurn, Bind ValidateOwnership, Bind ValidateAction
  alt command is legal
    R->>S: Simulate: new Simulation(before.DeepCopy())
    S->>S: Apply(command), Drain(), CheckVictory()
    S-->>R: new State and Events
    R-->>A: Result.Ok(CombatResolution)
    A->>A: StartCoroutine(Present(command, resolution))
    A->>V: AnimateCommand(before, command)
    A->>A: State = resolution.State, Sound(command, Events)
    A->>V: Render()
    A->>V: AnimateEvents(before, Events)
    A->>A: PresentFinish(command)
  else rejected
    R-->>A: Result.Fail(RuleError)
    A->>A: Notify(Error.Message), State unchanged
  end

ExpeditionApp.Submit, ResolveLocal, Present and PresentFinish are in ExpeditionApp.cs. SelectionCommands filters the cached CombatRules.LegalCommands list (CachedLegalActions in ExpeditionApp.Queries.cs). AnimateCommand and AnimateEvents are in ExpeditionView.Motion.cs.

The rival's turn

ExpeditionApp.Update plans with CombatAi.Choose, waits, then calls the same ResolveLocal. A practice tutorial substitutes its scripted PracticeOpponentCommand.

A networked match

Submit hands the command to network.Submit. The host's ExpeditionAuthority.Receive checks seat, sequence and fingerprint, then calls the same CombatRules.Resolve. See Networking.

Where the match starts

A Circuit table goes through PrepareTable (ExpeditionApp.Session.cs). It calls BeginEncounter, whose NewMatch state it then replaces with FairMatchSetup.CreateFairMatch, which wraps a second NewMatch. Practice and lesson sessions run the same PrepareTable; its last step, PreparePracticeTutorial, replaces that state with LessonRules.Prepare for a lesson or its own NewMatch for the practice tutorial. Local Versus (NewLocalDuel) calls NewMatch directly. See Hosted Sessions.

The guide's version of this flow, with the rules for handles, effects and turn order, is One accepted command.

07Progression: what is still live and what is retired

EmberGrove.Expedition.Progression was the rules for the standalone Expedition campaign. The campaign shell is gone, but the assembly still holds the content-pack type the whole game loads. A search of Game/EmberGrove/Assets on main finds no use of the campaign rules.

Still used by the game

  • ContentPack (ExpeditionRun.cs): Cards, MatchRules, MatchDeckSize, Encounters, DeckPresets, World; CreateCatalog(), Encounter(id), Card(id), DeckPreset(id), Validate().
  • EncounterDefinition: an opponent's ID, title, intent hint, life and deck. Each Circuit opponent names one through CircuitOpponent.EncounterId.
  • DeckPresetDefinition: the Versus and network deck choices.
  • WorldDefinition and RouteKind: at runtime, read only by ExpeditionApp.Media.cs (TickMediaBossEncounter) to pick boss music. IsometricSliceBuild also parses and validates the world when it stages content.
  • CombatProgressFacts: built by ExpeditionAuthority after each accepted network command. The game does not read the facts.

Retired campaign shell (no game callers)

  • RunState, RunRules, RunResult<T>, RouteNode, RelicDefinition, RunPhase (ExpeditionRun.cs).
  • ProfileState, ProfileRules, StoryRules, WorldResult<T>, progress envelopes and receipts (WorldProfile.cs).
  • CampaignRules (CampaignRules.cs) and most of WorldDefinitions.cs (campaigns, story scenes, codex, tutorials, achievements, unlocks).
  • Callers left: the package sample Samples~/MinimalTactics/MinimalProgression.cs, Tools/Expedition/CampaignChecks.cs and WorldChecks.cs (the LegacyProgression suite), and Tools/ExpeditionPerformance/WorldFactChecks.cs.
The retired data is still loaded and validated. ExpeditionContent.Parse runs ContentPack.Validate(), which still requires a starter deck of at least five cards, the four route encounter IDs (OpeningEncounterId … BossEncounterId) and valid relics. The game never reads the route IDs or relics. StarterDeck survives only as the last fallback deck in PrepareTable and SelectedDeck. ContentPackFiles then parses world-content.json with WorldContent.Parse and runs pack.World.Validate(pack) on every pack load. So the current pack has to carry campaign-era data to load at all. See Findings.

The guide's own account of what RunRules and ProfileRules did, and that they are not the Circuit save model, is Run and profile state. The second flow in ARCHITECTURE.md, Runtime flow (CombatProgressFacts into ProfileRules.ApplyBatch) describes the retired campaign, not the current game.

The transitions share one shape. Most start with Ready (or Editable for saved decks), which runs the full Validate(definition, state) and deep-clones the state; ResolveDuel, AbandonRun, CommitEvent and SelectTask do the same two steps inline, and Start, StartFromDeck and StartNextRun build a new state. The rule then changes only the copy and returns Result<CircuitState>.Ok(copy), or a failure whose code starts with circuit.. The caller's object is never touched, so a failed command needs no rollback. The module guide owns the rules themselves: state and content, core transitions, world and tournaments, rewards and saves and recovery.

09The ApplyCircuit pattern on the game side

The game keeps the adventure in one place, CircuitProgress.State, which IsometricSlice reads through its get-only circuit. During play it changes the adventure through one method, ApplyCircuit(EmberGrove.Result<CircuitState> result, bool requireSaved = false, bool restoreAtArrival = false) in IsometricSlice.Circuit.cs. Every caller passes it the result of a CircuitRules transition. StartCircuitFromDeck shows why that is a Result: it passes AbandonRun(…).Bind(left => StartFromDeck(…)), so leaving the old day and starting the new one are saved together or not at all.

// IsometricSlice.Circuit.cs, PlayCircuitDuel
if (!ApplyCircuit(episode == null ? CircuitRules.BeginDuel(circuitDefinition, circuit)
    : CircuitRules.BeginEpisodeDuel(circuitDefinition, circuit, episode.Id), requireSaved: episode != null)) yield break;
  1. Failure: the RuleError.Message becomes circuitNotice, an open journal page is redrawn, and the method returns false. The state is unchanged.
  2. Success: CircuitProgress.Apply keeps the old state, makes result.Value the State, and moves the selection to the next task when the selected task has just finished.
  3. Save: Apply then calls SaveCircuit once, which writes the whole CircuitSave through CircuitProgress.Write and CircuitPersistence (see Saves & Settings). With requireSaved, a failed write puts the old state back, so a story choice stays retryable until it is on disk. restoreAtArrival saves a new day without the world position.
  4. Refresh: the objective text, landmarks and prompt are updated.

Callers are in IsometricSlice.Circuit.cs, .CircuitUi.cs, .DeckBuilder.cs, .Learning.cs and .World.cs. The world, journal and HUD around it are described on World & Journal.

Where the adventure is assigned without ApplyCircuit. At load time RestoreCircuit sets it through CircuitProgress.Restore (the restored save) and CircuitProgress.EnsureRun (a fresh NewProfile, the first Start/StartFromDeck, a ResolveDuel(…Interrupted) safety net), and in editor or QA builds the testing top-up CircuitSliceChecks.TopUpTestingSave. Inside ApplyCircuit, the task advance in CircuitProgress.Apply sets it from SelectTask. The rule calls among them read .Value without checking IsSuccess, so a failure there throws instead of showing a notice.

The guide states the ownership split, rules in CircuitRules, the adventure in CircuitProgress and disk in CircuitPersistence, in Run and profile state. MAINTAINING, Change behavior at its owner is the rule against computing rewards or damage a second time in a menu.

10A duel receipt, from begin to resolved

A Circuit duel crosses the boundary twice: out into a hosted battle, and back with a result. The receipt makes the return safe. BeginDuel issues a deterministic ReceiptId on the pending duel. ResolveDuel applies an outcome only for that exact receipt. Once applied, the receipt is remembered, and a repeat returns an equal copy that grants nothing.

stateDiagram-v2
  direction LR
  [*] --> Pending : BeginDuel or BeginEpisodeDuel
  Pending : Pending - Run.PendingDuel holds ReceiptId
  Pending --> Pending : ResolveDuel with another receipt fails (circuit.receipt)
  Pending --> Applied : ResolveDuel(receipt, outcome)
  Pending --> Applied : AbandonRun
  Pending --> Applied : Recover on load clears it
  Applied : Applied - PendingDuel is null, receipt in Run.AppliedReceipts
  Applied --> Applied : ResolveDuel(same receipt) returns an equal copy
  Applied --> Dropped : 64 newer receipts
  Dropped : Dropped - ResolveDuel fails
  Dropped --> [*]

The receipt is r{Number}-{Seed}-s{Stage}-duel-{DuelNumber} (Receipt in CircuitRules.cs). RememberReceipt keeps the last 64. A story-match receipt also stays matched through its CircuitEpisodeRecord, which ResolveDuelApplied checks too.

What an applied outcome changes depends on the duel. A story duel (one with an EpisodeId) records its first Won or Lost result as an episode record and nothing else. For an ordinary duel, Won counts the win, advances the qualifying or tournament count and calls GrantReward, which sets PendingReward; Lost and Abandoned end the run; Interrupted and Drawn only clear the duel so the table can be replayed. The rules for each outcome are in Outcomes and receipts.

Its Build(state, definition, template, …) projects the retained Circuit districts into one SectorDefinition window, and IsometricSlice.MakeCircuitSector calls it. The World check suite compiles that file straight from the game folder.

The toolkit README's package boundary table lists "Circuit world layout" under CardForge.Exploration. On main, that code is CircuitWorldLayout in the game, and the toolkit assembly has no Circuit reference. The supported layout versions are owned by MAINTAINING, Supported Circuit world layouts.

12The checks that compile this layer

The rules run without Unity, so most of their tests are .NET console projects under Tools/, run through Tools/Run-Checks.ps1 -Suite <name>. Each project compiles the toolkit source files by path; it does not reference the Unity assemblies.
