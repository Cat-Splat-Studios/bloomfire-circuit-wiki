How players connect

The three multiplayer routes in Bloomfire Circuit (LAN, the WebSocket relay and the trusted loopback service), the one authority they share, the wire format, and the checks that exercise them.

In 60 seconds

  • One authority type. ExpeditionAuthority holds the full CombatState of a two-player match. ViewFor(seat) is the only way state leaves it, as a redacted WireView, and Receive(seat, packet) is the only way a command enters it. §04.
  • One client type. ExpeditionNetworkSession implements every route. Socket and HTTP work runs on background tasks and only queues notices; Poll() on the Unity main thread applies them and raises SnapshotChanged. §05.
  • Three routes. LAN TCP on port 47777, where the host's session runs the authority (§06); the WebSocket relay in Tools/ExpeditionRelay, which forwards bytes and never simulates (§07); and the trusted service (the same executable started with --authority), which runs the authority for matches, quickmatch and the table lobby (§08, §09).
  • Admission is a content check. LAN and relay peers compare ExpeditionFingerprint in a Hello packet. The trusted service also compares the protocol, rules version, content version and content SHA-256, and for the lobby the SHA-256 of Content/Circuit/locations.json.
  • Wire format. ExpeditionWireCodec uses DataContractJsonSerializer with a 64 KiB cap per packet. The relay and the trusted service read their own envelopes with System.Text.Json. §10.

Before you start

  • Know how a battle resolves a command: Rules Engine (CombatRules, CombatState, CombatCommand).
  • Know what a hosted ExpeditionApp is: Hosted Sessions. The connection menus are drawn by ExpeditionView.Connection.cs (UI & Menus).
  • The rules, procedures and limits belong to the guides. This page explains how the code fits together and links them: NETWORKING.md, the relay tool guide and the toolkit's multiplayer integration notes.

04The authority and its views

ExpeditionAuthority is a plain class with no transport. Its constructor takes a catalog, a preset dictionary, the two preset IDs, a seed, an optional CombatConfig and an optional match ID, then calls CombatRules.NewMatch. The full state is never returned to a seat: it sits in internal fields (state, lastEvents, lastCommand) that only the portable checks read, because WorldFactChecks compiles the toolkit source and ExpeditionRelay gives ExpeditionNetworkChecks InternalsVisibleTo. Seat 0 plays the first deck and seat 1 the second.

The fingerprint

ExpeditionFingerprint.Compute(catalog, presets, config) is a lowercase SHA-256 over a binary stream of: ExpeditionProtocol.Version, RulesVersion, CombatRules.Version, the CombatConfig fields, every card sorted by ID (title, rules text, kind, cost, attack, health, art index, range, target and each effect), and every preset sorted by ID. The finite-deck settings (OpeningHandSize, SpentCardsStayDiscarded, EmptyDrawDamage) are written only when one of them differs from its default, so the default byte stream matches earlier releases. ValidatePresets requires 1 to 32 presets of equal size, at least 5 cards each, and no upgraded cards.

ViewFor(seat): what a player may see

A WireView holds the public board, the side totals (WireSide: life, shield, pulse and zone counts), the viewer's own hand, the cards the viewer may see (WireCard), the legal commands (only on the viewer's turn), the last command and events, and that seat's public progress facts. Cards are addressed by viewer-local handles, never by simulation IDs. Each seat keeps its own handle maps; RefreshHandles issues handles for cards the seat can see (board, own hand, discards) and retires the rest. When an accepted command draws cards, the drawn cards' old handles are retired for both seats, so a card that was public cannot be tracked back into a shuffled deck. Toolkit NETWORKING · Render a private player view and the architecture guide own the privacy rules.

Receive(seat, packet): the order of checks

The seat argument comes from the connection (the host's own input is seat 0, the LAN or relay guest is seat 1, a trusted ticket names its seat), never from the packet. Checks run in this order, and the first failure answers with a code:

From view to screen: ExpeditionProjection

ExpeditionProjection.ToSnapshot(view, catalog, initial) first runs Validate: header bounds, the config, array sizes, turn bounds, then the hand limit, the side totals, each card, the own hand, every command, event and progress fact. Only then does it build an ExpeditionSnapshot: a CombatState whose hidden zone entries are -1, whose unseen handles are empty placeholder cards, and whose RngState is 0, plus the legal commands, events, progress facts, last command, revision, viewer seat and match ID. That state is for drawing only; the game submits commands from LegalCommands and must never pass the snapshot state to CombatRules or the AI.

Samples~/MinimalTactics/MinimalNetwork.cs exercises the authority, the codec and the projection without a socket.

05The session: one class, every route

ExpeditionNetworkSession is built once per connection attempt from a catalog, the preset dictionary, the player's preset ID, a host seed and the match rules, plus two optional HttpMessageHandler seams for tests. It computes the fingerprint in its constructor. One entry method starts it; a second call throws "Create a new session before connecting again."

Threading: background I/O, main-thread Poll

  • Accepts, connects, read loops and HTTP requests run as tasks and never apply their results to session state themselves. Each result becomes a private Notice pushed onto a ConcurrentQueue.
  • Poll() drains at most 32 notices per call and applies them. The snapshots, status changes and errors those notices carry, and the SnapshotChanged event, are applied only inside Poll. On the trusted route, control state (tickets, pending commands) is committed before the event fires, so a handler that disposes or suspends the session cannot be undone by the rest of that notice.
  • Submit(command) builds a Command packet with the next sequence and the current revision. A LAN or relay host queues its own command for the next Poll; a guest sends it; a trusted client stores it as the pending envelope. Only one command can be pending.
  • Dispose() cancels everything and releases the listener, link and HTTP client.

Toolkit NETWORKING · Transport lifecycle states the same contract for package users.

The two links

NetworkLink serializes sends with a semaphore, allows at most 32 outstanding sends and rejects empty or oversized payloads. TcpNetworkLink frames each packet with a 4-byte big-endian length and sets NoDelay. WebSocketNetworkLink sends text messages and accepts only text messages up to a byte cap (64 KiB by default, smaller during named-room setup).

Client-side bounds on LAN and relay

These live in Push, Poll, PollNotice, PollTimers and PollDeadlines. The queue limit applies to every session; the others apply to LAN and relay only, because a trusted session leaves Poll through PollTrusted before the rate check and timers run.

Any failure calls Fail, which ends the session for good (Ended). LAN and relay have no resume; ExpeditionApp.ConnectionLost reports that case, so the match no longer counts as in progress and Back leaves it at once (BackTakesOnlyExit).

How the game uses it

  1. ExpeditionApp.StartNetwork builds the session from Content.DeckPresets, ChosenDeckId, Environment.TickCount as the seed and Content.MatchRules, subscribes QueueNetworkSnapshot, then calls the chosen entry method. In the editor and QA players it also passes ExpeditionHarness handlers.
  2. ExpeditionApp.Update calls PollNetwork, which calls network.Poll(), mirrors status and errors to the view, and starts PresentNetwork for the next queued snapshot with a higher revision.
  3. When the player acts, ExpeditionApp calls network.Submit(command) instead of resolving locally.
  4. DisconnectNetwork unsubscribes and disposes the session, unless the session is borrowed from the table lobby (§09).

06LAN: host, join and the Hello

HostLan(port) opens a TcpListener on IPAddress.Any with a backlog of one, accepts a single client and stops listening. JoinLan(address, port) connects with a 10-second timeout. Neither side compares the content file's SHA-256: the fingerprint is the whole admission check.

  • The guest sends Hello (its fingerprint and preset ID) as soon as its link opens. On the relay it waits for the relay's PeerReady instead.
  • ProcessHello on the host rejects a second Hello, a different fingerprint or an unknown preset by sending Error with code content and failing its own session.
  • On a match the host constructs new ExpeditionAuthority(catalog, presets, ownDeckId, packet.DeckId, seed, config), delivers ViewFor(0) to itself and sends View with ViewFor(1) to the guest.
  • After each accepted command the host delivers its own view and sends the guest's. A rejected guest command gets Error with the code and a fresh ViewFor(1); the guest shows fixed local text for the code and never displays the host's message text (RejectionMessage).
  • The guest checks every view: seat, fingerprint and agreed CombatConfig (DeliverConfigMismatch), match ID and revision never moving backwards (DeliverMovedBackwards), then ExpeditionProjection validation.

ExpeditionApp.HostLan also adds a "Host address" hint listing up to three local IPv4 addresses. The player procedure for a real two-device test is in NETWORKING.md · First physical Android-Windows LAN test.

07The relay server

The relay pairs two WebSocket peers in a room and forwards their game packets. It never decodes a command or a view. The host's session is still the authority, exactly as on LAN; the relay only fixes who may send which packet kind.

Startup and hosting

  • RelayApplication.Create(args) builds an ASP.NET Core WebApplication with Kestrel limits, maps GET /health and /relay, starts a housekeeping loop (every 10 seconds it removes expired rooms and prunes the address limiter) and returns a RelayRuntime.
  • RelayRuntime wraps start, stop and dispose, and Endpoints() lists the addresses players can use ("This computer", a configured address, and each active IPv4 address when the listener is a wildcard).
  • RelayOptions.Parse reads --port (default 5078), --bind lan|local (default lan), --urls, --interactive and --help. RelayConsole.RunAsync is the console host; the Windows companion and its --headless mode use the same pieces.

Kestrel limits, rate buckets and room lifetimes are owned by the relay guide · Cross-platform source host. The companion's operator steps are in NETWORKING.md · Start the Windows relay companion.

/health

Returns status, gameplay protocol, relayProtocol, roomProtocol, sourceRevision (the RENDER_GIT_COMMIT environment value if it is a 40-character hex commit, otherwise empty) and aggregate counters: activeRooms, activeConnections, rejectedRequests, rejectedMessages, expiredRooms. Before any non-loopback relay connection or room listing, the client's WaitForRelayReadyAsync probes /health (over https for a wss endpoint) and checks those protocol numbers. One process-wide worker runs the probe so a stuck platform call stays off the player thread. The waiting budget and retry rules belong to NETWORKING.md · Named public and private rooms.

/relay: admission

RelayService.Relay handles each upgrade. The query is only role=host, role=join or role=list. Admit runs its gates in this order:

  1. Access gate (RelayAccess.Allows). The server reads two environment variables, BLOOMFIRE_RELAY_ACCESS_HASH and BLOOMFIRE_RELAY_ACCESS_EXPIRES_UTC; setting one without the other, or a malformed value, stops startup. With a gate configured, the X-Bloomfire-Relay-Access header must match it before the expiry. With no gate, only ungated local QA is admitted: every configured listener and the remote address must be loopback (LocalQa). Relay guide · Closed-test runtime access owns the setup.
  2. Request budget (RelayAdmission.Browse for lists, Attempt otherwise).
  3. Request shape: a WebSocket request, one role, one protocol header of 2 or 3 (listing needs 3), and an invitation header only on a protocol-2 join.
  4. Create or join budget, then a connection slot for the address.

Two room kinds

Invitation rooms (protocol 2)

A host gets RoomCreated carrying a random 32-character RoomCode. A guest sends that code in X-Bloomfire-Relay-Invite; a join to an unknown code gets HTTP 404 before the upgrade. Both peers then get PeerReady. These rooms are never listed.

Named rooms (protocol 3)

After the upgrade the client sends one RelayRoomSetup text message (HostRoom, JoinRoom or ListRooms) within five seconds. RelaySetup.Read accepts only known fields. Private room passwords become a PBKDF2 verifier on a single worker. A host gets RoomCreated (room ID and name) before the room is published; a guest gets RoomJoined, then both get PeerReady. A list request gets one RoomList of waiting public rooms and the socket closes. Setup failures answer RoomRejected with a code. Relay guide · Named-room protocol 3 owns the name, password and listing rules.

Forwarding

Forward reads each message with a 35-second timeout and per-peer message and byte buckets. A message must be a JSON object with exactly one numeric Protocol equal to 1 and one string Kind (EnvelopeKind). Ping is answered by the relay with Pong and goes no further. RelayRoom.Allow then fixes direction: nothing is forwarded until the guest's single Hello; after it the guest may send only Command, and the host only View or Error. Anything else ends the room. When either peer leaves, EndRoom removes the room and tells the other peer PeerLeft; the client then fails with "The other player left the room."

08The trusted authority

Started with --authority --content FILE [--port 5079] [--lobby locations.json], the same executable runs TrustedMatchApplication: an HTTP service where the server, not a player, owns every match. It binds IPAddress.Loopback only, ignores listener URLs from the environment and clears all logging providers. The client refuses any endpoint that is not loopback http or https with path /.

Loopback-only is deliberate on both sides. The trusted route is a local proof; how it was exercised across devices, and what is still missing, is in NETWORKING.md · Trusted service proof and remaining online work.

The registry: TrustedMatches

  • Built once from the content file text: ExpeditionContent.Parse, then the catalog, presets and MatchRules. It pins the content version, the SHA-256 of the file's UTF-8 text, and ExpeditionFingerprint. With --lobby it also reads the file's Lobby object, requires exactly one cardtable landmark, and pins that file's SHA-256.
  • All matches, queue entries, visitors and tables sit behind one lock. TrustedMatchRuntime runs Sweep every 500 ms (expiry, silent seats, queue pairing).
  • Each participant is a Player object: a random 64-hex token, a session generation starting at 1, and a resume ID. A resume with a fresh X-Match-Resume-ID increments the generation, which fences the old connection; repeating the same resume ID is accepted as a retry. The same Player carries a participant from queue or lobby into the match, so the match ticket reuses the queue or lobby token.
  • AdmissionError is the one admission check: protocol, rules version, content version, content SHA-256 and fingerprint must match (else mismatch), and the preset must be known (else deck).
  • Commands go through the same ExpeditionAuthority.Receive. The first accepted command that produces a winner records a result ID, returned in the X-Match-Result header.

The client side of the trusted route

  • BeginTrusted validates the endpoint and content hash, builds one TrustedAdmission (protocol, rules version, content version, content SHA-256, fingerprint, preset, optional identity) and starts the first request. The game passes Content.Version and LoadedPack.CombatHash (ExpeditionApp.TrustedCombatHash).
  • At most one request is in flight (trustedBusy). StartTrustedRequest maps an operation name (create, join, view, command, resume, queue-create, queue-enqueue, queue-poll, queue-cancel, queue-resume, lobby-create, lobby-view, lobby-command, lobby-resume) to a route and body. Each request cancels itself after 10 seconds. Polling runs every 250 ms for a match or queue and every 100 ms in the lobby.
  • Replies are checked before use: ticket shape and continuity (same match, seat and token, session never lower), queue and lobby state names, and a result ID present exactly when the view has a winner. Older or duplicate views are validated and then ignored, never applied backwards.
  • SuspendTrusted bumps an epoch and cancels the request; notices from an older epoch are dropped in PollTrusted. ReconnectTrusted keeps one resume ID until a resume reply arrives, so a lost reply can be retried without fencing itself. A pending command envelope is kept and resent unchanged.
  • Transport failures, HTTP 408, 429, any 5xx, a 409 session, and in the lobby a 401 on a match route mark the session interrupted, which is the state RECONNECT uses (CanReconnect). Other HTTP rejections and undecodable replies end it (TrustedRequestProblemFatal, TrustedRequestFatal).

09The in-game table lobby

The table lobby is a small shared room served by the trusted service when it runs with --lobby. The world (IsometricSlice), not the hosted battle, owns the lobby's session; a battle borrows it for the length of a match. NETWORKING.md · Table lobby prototype owns how to start and play it.

The path through the code

  1. In the hosted Versus app, TABLE LOBBY calls ExpeditionApp.EnterTableLobby(endpoint), which finds the world with FindAnyObjectByType<IsometricSlice>() and calls OpenTableLobby(endpoint, ChosenDeckId).
  2. OpenTableLobbySession checks the lobby data (version, valid navigation, one cardtable landmark), builds a session from the Circuit content and calls JoinLobbyTrusted(endpoint, circuitContent.Version, circuitPack.CombatHash, lobbyContentHash). lobbyContentHash is the SHA-256 of the Circuit/locations.json text, computed when LoadCircuit reads it.
  3. If the Versus battle is still open it is cancelled; when it closes, ShowWorldVersus sees LobbyActive and calls InitializeTableLobby, which swaps in the lobby sector, builds the authored room and checks that its navigation and table position match the pinned data.
  4. Every frame IsometricSlice.Update calls TickTableLobby: poll the session (only while no battle owns it), place every member's traveller, send move commands while walking, rebuild the HUD when its signature changes.
  5. When the lobby ticket carries a match and its first view has arrived (TickTableLobbyMatchReady), PlayLobbyMatch seats both travellers, sets IsometricCombatBridge.LobbySession and plays a Versus session. Once the hosted app has a view, the bridge calls ExpeditionApp.AttachLobbyMatch(session), which subscribes to the borrowed session (borrowedNetwork) instead of creating one.
  6. After the battle, if the match is over, PlayLobbyMatch sends return. The reply has no match ticket, so the session clears its match state (PollTrustedLobbyLeaveMatch) and the player walks again.

While borrowed, ExpeditionApp.LeaveNetwork suspends the session instead of disposing it, and DisconnectNetwork leaves it alone; once the lobby is open, only ReleaseTableLobby disposes it.

Lobby state and commands

A member's state is not stored; TrustedMatches.LobbyState derives it on every reply, checking in this order. The HUD (DrawTableLobbyHudActions) offers buttons by state. Each table, search or return button sends a TrustedLobbyCommand through SubmitLobby; Walk to table only plans a route, and the walk then sends move. Table commands carry the table ID and the table revision the player saw; a stale revision is rejected.

10The wire format

Every packet is UTF-8 JSON. The game side reads and writes it with DataContractJsonSerializer through ExpeditionWireCodec; the server reads its own envelopes with System.Text.Json. The two meet on field names, so the names in NetworkContracts.cs are part of the protocol.

The codec

  • Encode/Decode handle WirePacket; EncodeTrusted<T>/DecodeTrusted<T> handle every other DTO. All four refuse more than MaxPacketBytes, and the decoders refuse empty input.
  • Decode also requires Protocol == 1 and a non-empty Kind of at most 32 characters. WirePacket.Protocol and Kind are [DataMember(IsRequired = true)], so a packet missing them fails to deserialize.
  • Two DTO styles exist. [DataContract] types (WirePacket, the relay room types, the Trusted* types) serialize only the members marked [DataMember]; the Trusted* types also set camelCase names to match the ASP.NET service. The payload types (WireView, WireCommand, WireCard, WireSide, WireEvent, NetworkProgressFact) are plain [Serializable] classes whose public fields serialize under their own names.
  • DataContractJsonSerializer writes enums (ActionKind, Zone, Rank, CombatEventKind, TerrainKind) as numbers, so enum order is part of the wire contract.
  • The serializer reports malformed JSON as SerializationException or System.Xml.XmlException, because it reads JSON through an XML reader. The client's filters that treat received data as invalid list both (PeerDataRejected, TrustedRequestFatal, RelayReadinessWorkerDecode). On the trusted service, CommandAction catches SerializationException and the IdentityHeader middleware turns an XmlException into 400 packet.
  • Size is not the only bound: ExpeditionProjection.Validate caps a view's cards, own hand, legal commands, events and progress facts, and checks every value range, before anything reaches the screen.

11Network QA at a glance

Networking is checked at three levels: .NET checks that drive the real session against the real relay and service, a socket runner that starts separate peer processes, and rehearsals inside a built player. QA & Rehearsals covers the whole QA system; the commands and evidence rules belong to the guides linked here.

Tools/ExpeditionNetworkChecks

A .NET 10 console that compiles ExpeditionNetworkSession.cs and references the relay project. With no arguments it runs the default Network suite (protocol rules, LAN safety probes, relay readiness and the trusted service, including synthetic identity cases). Named modes include trusted-checks, relay-rooms, relay-security, relay-cold-start, compare-player-reports. Checks README.

Run-SocketChecks.ps1

Builds the checks and the relay, then starts owned processes: a LAN host and guest (peer lan), a loopback relay, invitation, public-room and private-room peer pairs, and the guards, relay-security and relay-rooms probes. It removes the relay access variables from the child processes and refuses a non-empty output folder. Relay guide · Verification.

ExpeditionHarness.Network

Inside an editor or QA player: -expedition-net-verify <output> <host|guest> <mode> <endpoint> with mode lan, relay, relay-public, relay-private, trusted, quickmatch or lobby. -expedition-net-detached runs without a shared desktop folder and -expedition-net-faults drops accepted replies through the session's HTTP handler seam (CreateRehearsalHandler); both are for quickmatch and lobby only. On Android, ParseAndroidNetworkLaunch builds these arguments from the bloomfire.qa launch extra, for quickmatch or lobby only. It writes network-capture.json, plus named-room-capture.json for named rooms. Independent Unity player captures.

  • compare-player-reports FIRST SECOND HEALTH [--require-android] compares two players' captures with the authority's saved health. A single client's PASS does not pass a pair.
  • The harness reaches into production code only behind #if UNITY_EDITOR || EMBERGROVE_QA (for example in ExpeditionApp.StartNetwork and BrowseRelayRooms).
  • The private QA pair is built by Tools/Build-PrivateNetworkPair.ps1 with the environment variable BLOOMFIRE_PRIVATE_QA_RELAY_KEY and the ignored file Game/EmberGrove/Assets/Tests/Runtime/PrivateRelayQaSettings.generated.cs. Never paste their contents anywhere. MAINTAINING · Android development build owns that build.
  • Two-device procedures: NETWORKING.md · Mixed Windows–Android test plan and Internet prototype relay. What has been observed on which candidate is recorded in ROADMAP · Network and Android candidate evidence.
