Maintaining the wiki

How to build and check this wiki, where its sources are, what is generated, and what to update when the code changes.

In 60 seconds

  • Build: python Tools/Documentation/structure_wiki.py build, then open Builds/Documentation/Wiki/index.html in a browser (§01).
  • Check before you push: python Tools/Documentation/structure_wiki.py check prints PASS or lists every problem by group, and exits 1 if there is any (§03).
  • Edit sources, never output. Pages are hand-written in Docs/Wiki. The nav, diagrams.html and the complexity tables are generated on every build (§02).
  • Changed code? Find the change in the update matrix (§06) and fix the pages it names in the same commit.
  • Complexity comes from Tools/CodeMetrics. Whether its --max 9 check becomes a gate is the owner's decision (§07).

Before you start

You need Python 3 and Git on the path, and a .NET SDK, 10 or later, when the complexity tables have to be measured. Run every command from the repository root. Read AGENTS.md once: its one-source-of-truth rule is why these pages link the guides instead of copying them.

01Build and open the wiki

One standard-library Python tool builds the site from the sources and checks it. The output is plain static HTML that opens from disk with no server.

CommandWhat it does
python Tools/Documentation/structure_wiki.py buildBuilds into Builds/Documentation/Wiki (ignored by Git) and prints a JSON summary: pages built, NAV pages with no source yet, diagram counts and the measured revisions. It replaces that folder on every build.
python Tools/Documentation/structure_wiki.py build --out DIRBuilds somewhere else. It refuses to replace a folder that is not empty unless an earlier build wrote it.
python Tools/Documentation/structure_wiki.py checkCopies Docs/Wiki once to Temp/StructureWiki/check-source, builds that copy into Temp/StructureWiki/check and again into Temp/StructureWiki/check-repeat, compares the two and verifies the result (§03). Exit 0 means PASS.
--refresh-metrics (either command)Measures every reference revision again instead of reusing the cached complexity results (§07).

Open Builds/Documentation/Wiki/index.html in any browser. Diagrams render with the vendored mermaid.min.js, so no network is needed. With scripts off you lose the contents list, the previous/next links and the rendered diagrams; the diagram source stays readable as text.

Build problems are failures, never silent skips: a missing shell file, a page without its <!-- nav --> line, a missing complexity placeholder, a missing analyzer or .NET SDK, or a C# file the declaration reader cannot balance all stop the build with a message. A NAV page that has no source yet is only a warning on build, and a failure on check.

02Where the sources live, and what is generated

Everything you edit is under Docs/Wiki and Tools. Everything under Builds and Temp is output and is rebuilt.

PathWhat it isWho writes it
Docs/Wiki/*.htmlOne hand-written source page per NAV entry, except diagrams.html. The folder is flat and holds only pages and the four shell files; the build fails on anything else.People
Docs/Wiki/wiki.css, Docs/Wiki/wiki.jsThe shared shell every page loads: palette and components, and the script that builds the contents list and previous/next links and renders diagrams.People, rarely
Docs/Wiki/mermaid.min.js, Docs/Wiki/mermaid-LICENSE.txtMermaid 11.16.1, vendored unchanged with its MIT licence.Replaced deliberately, never edited
Tools/Documentation/structure_wiki.pyThe NAV table, the diagram generator, the complexity tables and their REVISIONS list, and the checker.People
Tools/CodeMetricsThe complexity analyzer the build runs (§07).People
Builds/Documentation/WikiThe built site.The build only
Temp/StructureWikiRevision snapshots, cached complexity results, the analyzer's build output and the check builds.The build and the check

What the build generates

  • The nav. Each source page carries the single line <!-- nav --> right after <body>; the build replaces it with the nav from NAV and marks the current page. No page carries its own copy.
  • diagrams.html, the whole page. It is drawn from the C# files, .asmdef files and tool .csproj files that git ls-files lists, so a new file appears only after git add, and an ignored file such as PrivateRelayQaSettings.generated.cs is never read. The reader sees declarations only and reads every #if branch as present.
  • The complexity tables. complexity.html holds six placeholder lines, <!-- complexity:summary -->, history, areas, bands, types and hotspots; the build replaces each with a table and fails if one is missing, repeated or unknown.
  • In the browser, wiki.js adds the “On this page” list and the previous/next links, read off the page's <h2>s and the nav order.

03What the check verifies

The check reports every problem it finds, grouped, and exits 1 if there is any. Each group below is a heading in its report.

GroupWhat fails it
BUILDThe build itself stopped; the message says why (§01).
MISSING PAGESA NAV page that was not built, with how many pages link to it.
NOT IN THE NAVA source page that has no NAV entry.
PAGE SHELLA source page without exactly one <!-- nav --> line, without wiki.css or wiki.js, without header.page (header.hero on index.html), main or footer, or without a .honest box (every page but index.html).
SECTION NUMBERSA section without an id or a number, or numbers out of order (§04). The generated page is checked too.
BROKEN LINKSA link to a page or #id that does not exist in the output, a link that leaves the wiki folder, a script or stylesheet that is not in the output, or an id used twice on one page.
REPOSITORY LINKSA https://github.com/Cat-Splat-Studios/CardGame/blob/main/… link whose path is not tracked on main, or whose #anchor is not a heading (by GitHub's slug rules) or an explicit <a id> in that Markdown file on main.
WRONG SECTION LABELSA §NN inside a link, or right after it, that does not match the number of the section the link lands in.
MERMAIDA page with a pre.mermaid that does not load mermaid.min.js, a page that loads it for nothing, or a raw < inside a diagram's source.
PRIVATE KEY PATTERNText shaped like the private relay credential: the escaped literal the private build writes, a quoted AccessKey constant, or a value given to BLOOMFIRE_PRIVATE_QA_RELAY_KEY. The match itself is never printed.
PUBLIC SITEText that must not reach the public site (§09): a path on a developer's machine (a drive path with either slash, a Git Bash, Cygwin or WSL path, a Linux or macOS home or volume, or a network share), an email address, an IP address other than loopback, a URL with a user name or password in it, or a link to a host that is neither loopback nor in PUBLIC_HOSTS. A host goes into that list only when it is a public site. For an example in prose, use a placeholder: a .invalid host, or a path whose machine-specific part is written as <folder>, such as <folder>/Tools.
NOT DETERMINISTICThe two builds, made from the same copy of the sources, differ: something in the build depends on time, order or the machine.

The check does not render Mermaid, so a diagram with a syntax error passes it; open the page and look. It does not follow links to other websites, and it cannot tell whether prose matches the code: the “Keep this page honest” box on each page lists the files to reread.

RuleDetail
Section numbersNumber sections 01, 02, … in order, each <section id="short-slug"> with <h2><span class="num">NN</span>Title</h2>. A section added between two others takes a letter instead of renumbering the rest: after 07 come 07b, 07c, then 08. Ids stay stable because other pages link them.
Citing a sectionWrite the number in the link: <a href="world.html#boot">world.html §02</a>. The check compares it with the target.
Repository filesLink a guide or file as https://github.com/Cat-Splat-Studios/CardGame/blob/main/<path>, with a heading anchor for Markdown. A link only passes once the file is on main, so a file new on your branch is named as <code> text until it merges. Source files named in prose are <code> text.
ComponentsUse only what wiki.css defines: .grid.c2/.c3 with .card.accent-*, tables in div.scrollx, .note, .note.warn, .note.rule, details.why, ol.steps, .kbd, pre code, .badge.*, td.num. No page-local <style>.
DiagramsHand-draw only the flows and state machines your page owns, each in div.diagram > pre.mermaid followed by p.caption, and load mermaid.min.js. Escape <, > and & inside the block. Keep one under about 25 nodes. Class diagrams are generated; link diagrams.html instead.
One source of truthExplain structure and how the pieces connect. Rules, procedures and tables a guide already owns get a sentence and a link to that guide's section, and the roadmap's status and decisions are only ever linked.
NumbersDo not write counts that change routinely (tests, cards, lines) into prose. The generated pages may, because every build recomputes them.
SecretsName BLOOMFIRE_PRIVATE_QA_RELAY_KEY and PrivateRelayQaSettings.generated.cs if you must, never a value.

05Adding a page

A page exists for the wiki once it has a NAV entry, a source file and a passing check.

  1. Add the NAV entry. In Tools/Documentation/structure_wiki.py, add ("Group", "Label", "file-name.html") to NAV where it belongs in reading order, next to the other entries of its group: the nav opens a new group box wherever the group name changes. The file name is lowercase kebab-case, and diagrams.html is taken by the generated page.
  2. Write the source page at Docs/Wiki/file-name.html in the shape of §04, with its own path in the footer and the files it describes in its honest box.
  3. Give it a card on the home page, in index.html §03, in the same group as the nav, and add its new terms to the glossary.
  4. Add a row to the update matrix (§06) for the code the page describes.
  5. Run the check and fix every group it reports, then build and read the page in a browser.

Retiring a page is the same in reverse: remove the NAV entry, the source, its card and its matrix rows, and fix the links the check then reports.

07How complexity is measured

Tools/CodeMetrics parses C# with the Roslyn parser that ships in the .NET SDK, so it downloads no package. The definitions of every metric and its default preprocessor symbols are in the header comment of Tools/CodeMetrics/Program.cs and nowhere else; complexity.html explains the results.

Run it yourself

dotnet run --project Tools/CodeMetrics/CodeMetrics.csproj -c Release --artifacts-path Temp/CodeMetrics/build -- --root . --out Temp/CodeMetrics/metrics.json
dotnet run --project Tools/CodeMetrics/CodeMetrics.csproj -c Release --artifacts-path Temp/CodeMetrics/build -- --root . --out Temp/CodeMetrics/metrics.json --max 9
OptionMeaning
--root DIRThe checkout to measure. It scans Toolkit, Tools, Teaching and Game/EmberGrove/Assets below it, skipping bin, obj, Library, Temp and Builds folders. On your working tree that includes files Git does not track.
--out FILEWhere the JSON array of member records goes: file, area, type, member, line, cyclomatic complexity, cognitive complexity, nesting and lines.
--define NAMEA preprocessor symbol, repeatable. Giving any replaces the default set.
--max NPrints every member body whose cyclomatic complexity is over N and exits 1. --max 9 is the “below 10” check.

What the wiki measures

The build measures committed revisions, not your working tree. For each entry in REVISIONS in structure_wiki.py (three reference revisions and HEAD) it extracts git archive <revision> -- Toolkit Tools Teaching Game/EmberGrove/Assets into Temp/StructureWiki/snapshots/<sha>, runs the analyzer there with its default symbols, and caches the result as Temp/StructureWiki/metrics-<sha>.json. A cached result is reused until the commit or the analyzer's source changes; --refresh-metrics measures again regardless. Each build deletes the snapshots and results of revisions it did not measure, such as an earlier HEAD. There is no fallback: without Tools/CodeMetrics or the .NET SDK the build fails rather than leaving tables out.

Not a gate yet. Nothing runs --max 9 automatically. Whether it becomes a required check is the owner's decision, recorded in the roadmap's open owner decisions.

09Publishing the public site

The wiki is public, at cat-splat-studios.github.io/bloomfire-circuit-wiki. The sources stay in this private repository, and a GitHub Actions workflow pushes the built site to the public repository Cat-Splat-Studios/bloomfire-circuit-wiki, whose Pages site serves it. The Sentinels of Gleamwood wiki is published the same way.

Everything on a page is public the next time it is published. Do not write credentials, private hosts, addresses or machine paths, people's names, or plans that have not been announced. The check fails on the shapes it can recognise (PUBLIC SITE and PRIVATE KEY PATTERN, §03); the rest is up to the author.

WhenWhat .github/workflows/publish-wiki.yml does
Every push to mainRuns structure_wiki.py check on Linux, with the .NET SDK for the complexity tables. A red mark on the commit means a page, a link or a generated table broke; fix it in the next commit. A push publishes nothing.
Run by hand on main (a run started on another branch does nothing)Runs the same check, and when it passes pushes the checked output to the public repository's gh-pages branch as one commit titled Sync wiki from <sha>. Start it from Actions ▸ Publish Wiki ▸ Run workflow, or with gh workflow run publish-wiki.yml --ref main. Pages takes a minute or two to serve the new copy.

Publishing is manual so that pages can change over several commits and the site keeps the last set somebody chose to publish. The earlier revisions' complexity measurements are cached between runs, so once one run has passed, a run measures only the current commit. A new cache entry is saved when the analyzer or structure_wiki.py changes, and the build deletes the measurements of revisions it no longer uses.

The one-time setup, and rotating the key

  1. The public repository Cat-Splat-Studios/bloomfire-circuit-wiki exists. It has only the gh-pages branch the workflow writes.
  2. An SSH deploy key with write access is on that repository (Settings ▸ Deploy keys). It can write to that one repository and nothing else.
  3. The private half of that key is the Actions secret WIKI_DEPLOY_KEY on this repository.
  4. Pages on the public repository serves the gh-pages branch from /.

To rotate the key, make a new key pair, replace the deploy key (step 2) and the secret (step 3), delete the old deploy key, and run the workflow once to prove it.
