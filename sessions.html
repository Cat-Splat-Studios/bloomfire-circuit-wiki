How a table session runs

How the Circuit world hands a duel, a practice, a lesson, the Versus menu or the Settings screen to a throwaway ExpeditionApp, and how the result comes back and gets saved.

In 60 seconds

  • Every table is a throwaway app. IsometricCombatBridge.Play builds an inactive Hosted session GameObject, adds an ExpeditionApp, configures it for one HostedSessionKind, then activates it. Start loads the content pack, builds the match and adds ExpeditionView. §02 §03
  • One command path. Local player moves and rival moves both end in ResolveLocal → CombatRules.Resolve → Present, which runs AnimateCommand, Render and AnimateEvents. The rival chooses with CombatAi.Choose. Practice uses a scripted partner instead. §04
  • A duel result is committed twice, on purpose. The world applies CircuitRules.ResolveDuel as soon as the match is over, before the player leaves the result screen, then again after Play returns. The duel's ReceiptId turns the second call into a no-op. §05
  • The screen is decided, not stored. No enum says which screen is showing. ExpeditionView.Render works it out each time from Kind, State and booleans spread across seven ExpeditionApp files and the view. §06
  • A session borrows the world and gives it back. It draws on the world's table through WorldTableContext. The bridge snapshots quality, frame rate, vsync, render pipeline, volume, cursor and EventSystem before the session and restores them afterwards. §08 §09

Before you start

Read the Codebase Tour for where the game and the toolkit sit, and Rules Engine for CombatRules, CombatCommand and CombatState. This page starts where the world (World & Journal) decides to play a table. It ends where the result is saved (Saves & Settings). Network play inside Versus is on Networking, and the view's drawing and input routing are on UI & Menus.

01Where the pieces live

All session code is game code in Game/EmberGrove/Assets/Runtime. The game has no asmdef, so it compiles into Assembly-CSharp. The bridge sits with the world in Exploration/ (namespace EmberGrove.Exploration). The session itself is in namespace EmberGrove.Expedition, a name left over from the retired standalone mode (CODE_ARCHITECTURE_GUIDE · Product names). The rules it calls (CombatRules, CombatAi, LessonRules, CircuitRules) live in the CardForge toolkit.

LocalDuel and the network session are what is played inside Versus, and they are not kinds.

03Opening a session

A launcher fills in the bridge and yields on Play. Play builds the host while it is inactive, so the configure calls finish before Awake and Start run. It then polls each frame until the session ends.

  1. Launcher. It sets inEncounter and fills the bridge fields. Every launcher except the lobby match (PlayLobbyMatch) also closes the journal, shows the "Shuffling decks…" cover (ShowEncounterLoading, which adds a Cancel button only while a Circuit duel is pending) and takes the table lease (PrepareWorldTablePresentation). Most launchers then move the camera (BeginWorldTableSessionView, §08).
  2. Play(encounterId, completed, receiptId). It throws if a session is already Active. It resets Error, ResultSettings and PracticeCompleted, sets Outcome to Interrupted, stores ReceiptId and snapshots global state into a RuntimePreferences (§09).
  3. Begin. It creates new GameObject("Hosted session"), deactivates it and parents it to the bridge. Then it calls AddComponent<ExpeditionApp>(), subscribes KeepWorldPipeline to SettingsChanged and calls ConfigureWorldTable(Table). It makes the configure calls for the kind (§02), adds PracticeNarration for Practice and Lesson, clears the EventSystem selection and finally calls host.SetActive(true). An exception here sets Error and ends the session at once.
  4. Awake → InitializeSettings. It reads the saved PlayerSettings, applies the saved display, then calls ApplySettingsRuntime. That sets the quality level, frame rate, vsync and listener volume for the whole process.
  5. Start (a coroutine). It calls ContentPackFiles.Load(sessionContentRoot ?? ContentPackFiles.DefaultRoot()), which loads the pack again even though the world loaded it at boot. It sets Content and Catalog = Content.CreateCatalog(), adds a GameAudioDirector, calls PrepareTable and InitializeMedia and makes sure a PlaytestSessionService exists. Last, it adds ExpeditionView and calls Initialize(this) and ApplyExternalTheme. Load or parse errors go into FatalError and do not throw.
  6. Poll loop. Each frame, PollSession ends the session if Session is gone or FatalError is set. While Session.View is still null, it also ends the session after 120 s of real time, or on Escape or the gamepad's east button. For the lobby, LobbyMatchReady attaches the borrowed network session once the view exists. On the world side, IsometricSlice.UpdateFrameEncounter hides the world canvas once combat.Session.View exists.

PrepareTable, step by step

It returns at once for Settings, for Versus, or if FatalError is set. Otherwise:

  1. It finds the encounter with Content.Encounter(sessionEncounter) and throws if it is unknown.
  2. It picks a deck: the chosen preset or Content.StarterDeck, replaced by the bridge's deck when one was configured. PrepareTableSessionDeck checks that deck with CombatRules.LegalMatchDeck.
  3. BeginEncounter resets selection, audio and timers, starts the playtest record (not in practice), and also builds a CombatState with the encounter's EnemyLife.
  4. The next line replaces that state with FairMatchSetup.CreateFairMatch(...), using Content.MatchRules and the configured opening bonus. A code comment states the intent: every table kind uses the same life, cards and resource rules as a default PvP match.
  5. PreparePracticeTutorial runs last. For Practice and Lesson it replaces State once more.

Any exception becomes FatalError = "The encounter could not be prepared. …". CombatRules.NewMatch and the other combat rules are on Rules Engine. The fair-setup suite is described in the CircuitFieldSetupChecks README.

04The turn loop

Each move goes through one guarded entry point and one presentation coroutine. The One accepted command section of the architecture guide owns the contract: the screen guards stop accidental input, and the reducer enforces the rules.

One local move, from input to settled board. The rival skips Submit and calls ResolveLocal directly. A networked session sends the command with network.Submit instead (Networking).

  • Submit drops the command unless CanAct is true, command.Player == Viewer and PracticeAllows(command). CanAct needs an unfinished State, no open menu, no lesson feedback waiting, no end-turn confirmation open (View.IsWorldReading), no card being inspected, and the turn owned by this viewer (§06).
  • ResolveLocal calls CombatRules.Resolve and records the action with Playtest (not in practice). If the rules reject the command, it shows the error with Notify and pushes the rival's next try back.
  • Present sets Busy and keeps the old state on screen while View.AnimateCommand runs. It then publishes resolution.State, plays sounds, calls Render and waits for View.AnimateEvents. PresentFinish clears Busy, plays the outcome cue if the match is over, sets Handoff after a local-duel end turn and advances practice (PracticeResolved).
  • The rival runs from Update. UpdateRivalWaits holds it while there is no state, the match is over, it is a local or network duel, it is player 0's turn, a screen is open (UpdateRivalScreenOpen), lesson feedback is waiting, or the end-turn confirmation is open or a card is being inspected (CanActViewIdle). UpdatePlanRivalCommand picks with CombatAi.Choose, or PracticeOpponentCommand in practice, and sets Intent. UpdateResolveRivalCommand plays it once nextAi has passed. In practice it also waits while PracticeNarration.HoldAutomaticAdvance() returns true.

05Result, FinishSession and the receipt

A session ends when FinishSession(outcome) calls the bridge's Complete. For Circuit duels, the world has usually committed the result before that, as soon as the match was over. After Play returns it commits again with the same receipt, and the rules ignore the repeat.

Teardown order

  1. FinishSession runs once (sessionFinished). Outside practice, it records an abandoned match with Playtest if the match is unfinished. It disables the app and the view first, so the same press cannot submit twice. Then it stops audio and playtest and invokes the stored callback once.
  2. Complete on the bridge stores Outcome and sets resolved. The poll loop exits, and its finally runs Release.
  3. Release takes the settings result (ReleaseSettings: unsubscribe, revert an unconfirmed display trial, FlushSettings, set ResultSettings). For Practice and Lesson it copies PracticeWon into PracticeCompleted. If State.IsOver, it replaces Outcome with Session.BattleOutcome, so the rules state wins over the callback. It then calls Session.ReleasePresentation(), clears a selection inside the host, deactivates and destroys the host and restores the global snapshot.
  4. One frame later, Play restores the snapshot again, clears Active and invokes completed(Outcome). The code comment explains the wait: the battle canvas, audio and focus targets must be gone first, so the world cannot consume the same confirming button press.

Why committing twice is safe

CommitFinishedCircuitDuel runs every frame during an encounter (UpdateFrameEncounter). It also runs from SaveProgress and SaveBeforeQuit. CircuitProgress.TryResolveFinishedDuel gives it a ResolveDuel result to apply only when PendingDuel exists, combat.ReceiptId matches it, and the outcome (Session.BattleOutcome once the match is over, otherwise combat.Outcome) is not Interrupted. So a result is recorded as soon as it exists, and quitting before Continue cannot lose it. When Play returns, PlayCircuitDuel calls ResolveDuel with the same receipt. ResolveDuelApplied finds the receipt in Run.AppliedReceipts (or in an episode record) and returns an unchanged copy, so nothing is granted twice. When the rules call succeeds, ApplyCircuit calls SaveCircuit, which writes through CaptureCircuitSave and CircuitProgress.Write.

Two related paths: a friendly game commits with requireSaved. If that save fails, ApplyCircuit keeps the previous state, EpisodeSavePending stays true and RetryEpisodeSave offers the same ResolveDuel again. And when a save is restored with a PendingDuel (the process quit mid-duel), RestoreCircuit resolves it as Interrupted (CircuitProgress.EnsureRun), so the player comes back to the challenge without a made-up result. See Saves & Settings.

07Practice, lessons and narration

Practice and Lesson are ordinary hosted sessions. They use a different starting State, a command filter and a scripted partner. Every move still goes through CombatRules.Resolve. The player-facing behaviour and the content files are owned by CIRCUIT_FIRST_STEPS and CIRCUIT_LESSONS. This section shows where that behaviour lives in the session.

Basic practice (ExpeditionApp.Practice.cs)

ConfigurePracticeTutorial(json) parses PracticeTutorialContent, the text from Circuit/practice.json that the world loaded at boot. PreparePracticeTutorial picks two simple units: the card ids named in that text if they qualify, otherwise the cheapest suitable catalogue cards. It copies Content.MatchRules with no opening hand and no empty-draw damage, and calls CombatRules.NewMatch with one card per side. The opposing heart total equals the player card's attack. Progress is the nine-value PracticeTutorialStep enum. PracticeAllows and PracticeCanSelect block every other move, and PracticeOpponentCommand scripts the partner.

Authored lesson (ExpeditionApp.Lessons.cs)

ConfigureAuthoredLesson rejects a lesson without a scenario (LessonRules.HasScenario) and keeps its own JSON copy of the definition. PrepareAuthoredLesson runs LessonRules.ValidateLesson, then LessonRules.Prepare for the state and the alias bindings. Each step's expected command comes from LessonRules.Command, and AuthoredAllows compares with LessonRules.Matches. After a matching move, AuthoredResolved shows the step's AfterPrompt. AuthoredLessonAwaitingContinue then blocks both the player and the rival until ContinueAuthoredLesson.

  • One instruction string. PracticeInstruction is the text both the view and the narrator read. It comes from the lesson step, the practice step or the waiting line.
  • Again, Skip, Finish. RestartPracticeTutorial stops coroutines, resets the screen and builds the practice again. It remembers an earlier win in practiceWonEarlier, so PracticeWon survives a replay. SkipPracticeTutorial finishes as Won if the practice was ever won, otherwise as Interrupted. FinishPracticeTutorial finishes as Won. All three reset PracticeNarration.
  • PracticeNarration is a sibling component on the host, added only for Practice and Lesson. Its Start loads StreamingAssets/Circuit/Voice/lines.json. When PracticeInstruction changes and the board has settled, it plays the WAV whose Text matches the instruction exactly. HoldAutomaticAdvance is what makes the rival wait for the line. Every load has a timeout (LoadTimeout), and mute or zero volume never holds the lesson. The content rules are in Spoken guide and Voice, coverage and limits.
  • What practice changes outside the session. Only presentation flags in the save, and never a receipt, deck or run. Practice and the real adventure owns that promise. The lesson guide's Integration and teaching architecture covers how the lesson library reaches the session.
Practice still goes through PrepareTable first. The launcher passes the first non-champion opponent's encounter and the run's active deck, and PrepareTableSessionDeck checks that deck with LegalMatchDeck. An unplayable run deck can therefore stop a practice that never uses it.

08The world table

A session can be drawn on the 3D table in the world, not only on a flat screen. The world lends the session a WorldTableContext. The view puts a world-space card canvas on the table and, if the venue has one, instantiates a WorldTablePresentation for creatures and terrain.

  1. Lease. IsometricSlice.PrepareWorldTablePresentation(landmarkId) returns the active context, or finds a table surface (the given landmark, else the nearest one). It saves the camera and builds new WorldTableContext(WorldCamera, anchor, size, landmarkId, visuals.LivingTablePrefab(landmarkId)), then seats the traveller and the opponent (StageWorldTableCharacters) and hides the table props. Versus lobby matches build their context with LobbyContext instead.
  2. Camera in. BeginWorldTableSessionView calls context.Frame(...) for the final camera pose and eases the camera there. With reduced motion it jumps.
  3. Hand-over. The bridge calls ConfigureWorldTable(Table) for every kind. UsesWorldPresentation is true when the context is Valid.
  4. Cards on the table. In each Render, ExpeditionView.PrepareWorldTable creates or updates the world-space canvas Physical card table, sized WorldTableContext.Width × Height. It is hidden during Handoff. Battle() switches to WorldTableBattle().
  5. Living table. RefreshLivingTable instantiates context.PresentationPrefab as Living table projections and calls Configure(context). While not Busy, it calls Reconcile(State, viewer, reducedMotion).
  6. Animation. ExpeditionView.AnimateCommand and AnimateEvents call the living table's versions first. WorldTablePresentation sets a pending flag so Reconcile keeps the old board until the events finish. Its class comment sums it up: snapshots reconcile resting pieces, and resolved events alone play reactions. CancelPresentation stops any running animation and reconciles to a given state. The view calls it on handoff, and RestartPracticeTutorial calls it on practice restart.
  7. Camera out. EndWorldTableSessionView eases back and calls ReleaseWorldTablePresentation. That restores the characters, traveller and camera, shows the props again and clears combat.Table.

The prefab comes from the authored venue bound to the landmark (IsometricSectorVisuals.LivingTablePrefab). Authored rooms and venues are on World & Journal.

  • When. The snapshot is taken at the start of Play. It is restored at the end of Release and again one frame later, just before the callback (§05).
  • During the session. ApplyRuntimePreferences can change the quality level, which can swap the render pipeline. On every SettingsChanged, the bridge's KeepWorldPipeline puts the world's pipeline back.
  • Settings the player changed. ReleaseSettings flushes them to PlayerPrefs and hands them out as ResultSettings: the session's normalized settings, or ExpeditionApp.ReadPreferences() if the host is already inactive. Each launcher then calls ApplyWorldPreferences(combat.ResultSettings). That re-applies the preferences on top of the restored snapshot and keeps the world's pipeline. So a change made in Settings survives the restore. Preference storage is on Saves & Settings.

10What to weigh when fixing

These are the structural points in this area that a fix would have to deal with. Each is checked against main. Findings ranks them against the rest of the codebase.

A full app per screen

Settings and the Versus menu get the same complete ExpeditionApp as a duel: a fresh ContentPackFiles.Load, a GameAudioDirector, media, a playtest service, saved preferences re-applied in Awake, and the whole snapshot and restore. Menu plans are tracked in the roadmap's Menus on UI Toolkit.

Screen state is implicit

The only statement of which screen is showing is the order of checks in Render, RenderScreen and RenderWindow. The six helpers in the §06 table, and others such as MoveHelpAvailableMenusClosed, keep overlapping flag lists. ResetScreen clears most flags by hand. An explicit screen state would replace those lists.

PrepareTable builds states it throws away

BeginEncounter builds a state that CreateFairMatch replaces on the next line. Practice and Lesson replace that state again. As a result, practice depends on an encounter id and a legal run deck it never plays (§07).

One result, two commit paths

The receipt makes it safe, but committing is split between CommitFinishedCircuitDuel (per frame and on save or quit) and PlayCircuitDuel after Play. Practice, Versus and Settings pass _ => { } as the callback and read the bridge's properties instead.

Code in files named for other types

ExpeditionView.ReleaseSessionSprites and FairMatchSetup sit in ExpeditionApp.Session.cs. ExpeditionApp.ConfigureWorldTable sits in WorldTableContext.cs. Tools/CircuitFieldSetupChecks/Run-Checks.ps1 cuts FairMatchSetup out of ExpeditionApp.Session.cs by searching for the text internal static class FairMatchSetup, so moving or renaming it fails that suite.

The session reaches back into the world

ExpeditionApp.EnterTableLobby finds the world with FindAnyObjectByType<IsometricSlice>() and calls OpenTableLobby. Two values must also agree: the bridge's public Kind field and the app's Kind property. They agree today only because Begin derives one from the other.
