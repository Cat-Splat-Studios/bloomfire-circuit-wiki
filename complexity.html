Code complexity

How branchy each C# member is, how that changed when every member was brought below cyclomatic complexity 10, and what that metric does not tell you.

In 60 seconds

  • The rule. Every C# member in the repository (toolkit, game, tools, QA tests and editor code) has a McCabe cyclomatic complexity below 10. The Now table is measured on every build, so it shows whether that still holds.
  • How it got there. Seven behaviour-preserving batches in November 2026 split long members into named steps called in the same order; nothing a player sees, saves or sends changed (§04).
  • What improved. The large, deeply nested members are gone: the share of complexity sitting in members over 10 fell from about two thirds to none, nesting and member length dropped, and the nesting-weighted cognitive total went down (§03).
  • What did not. Classes did not get smaller. The work moved branches into more members of the same classes, so IsometricSlice, CircuitSliceChecks and ExpeditionView carry as much total complexity as before (§06). That is the structural problem left, and Findings lays out the options.
  • Keeping it. Tools/CodeMetrics --max 9 fails when any member reaches 10. Whether that becomes a required check is an open owner decision (§09).

Before you start

The tables on this page are generated by Tools/Documentation/structure_wiki.py from Tools/CodeMetrics, measuring a git archive of each revision. The prose was written when the work finished; where it and a table disagree, the table is current.

01What is measured

One record per member body: methods, constructors, operators, accessors with a body, expression-bodied properties, property initializers and field initializers that branch. The analyzer parses the source with the Roslyn that ships in the .NET SDK, so it needs no package download.

MeasureWhat it countsWhy it is here
Cyclomatic complexity (CC)1, plus one for each if, non-default case label, switch-expression arm other than _, loop, catch, ?:, &&, ||, ??, ??= and the pattern combinators and/or. Lambdas and local functions count toward the member that contains them.The number of independent paths through a member: roughly how many cases a test needs and how much a reader has to hold. The owner's target was below 10 everywhere.
Cognitive complexityA simplified SonarSource measure: each branch or loop adds one plus its nesting depth, and each run of one logical operator adds one.CC treats a flat list of ten checks the same as ten nested branches. The cognitive score weights nesting, so it separates a long but simple validator from a genuinely tangled member.
NestingThe deepest stack of if, loops, switch, try, using and lock.Deep nesting is what makes a member hard to follow even when its CC is moderate.

Top-level statements count too: each top-level local function is its own member of Program, and the rest of the top-level code is Program.<Main>$. The scan covers Toolkit, Tools, Teaching and Game/EmberGrove/Assets, with the Unity editor and QA symbols defined (UNITY_EDITOR, CIRCUIT_QA, EMBERGROVE_QA, UNITY_STANDALONE_WIN, UNITY_STANDALONE), so code that only compiles for a player or for Android (#if !UNITY_EDITOR, #if UNITY_ANDROID) is not measured. Constructor initializers are not measured either. The definitions have one home, the header comment of Tools/CodeMetrics/Program.cs.

Why total CC is not the number to watch

Every member starts at 1. Splitting one member of complexity 40 into five steps of 8 leaves the branches where they were and adds a few new members, so the repository's total CC goes up while every member gets easier to read. The useful numbers are the per-member maximum, how many members sit above the threshold, how the members spread across the bands, and the nesting-weighted cognitive total.

Reading the tables

  • The tail is gone. Before the work, about two thirds of all the repository's CC sat in members above 10, and dozens of members were above 50 (the largest, the save-scenario script CircuitPersistenceVerification.RunScenarios, was 289). Now there is no member above 9.
  • There are about twice as many members. Each long member became a short parent plus named steps, so the member count roughly doubled and the mean CC per member roughly halved.
  • Readability measures moved the right way. The nesting-weighted cognitive total fell even though the code grew, members nested five or more deep went from about two dozen to a handful, and members over a hundred lines went from about seventy to almost none.
  • Total CC rose, as explained in §01, and the C# line count grew by roughly a fifth (new method signatures, braces and helper names).
  • Members bunch up below the line. Many members sit at 7–9 and a couple of hundred at exactly 9. A member at 9 crosses the threshold with one more condition, so new work in those members needs a split first.

04How it was done

Seven batches, each a separate pull request, each required to change no behaviour. Agents worked in isolated git worktrees, one group of files each, and every batch was verified as a whole before it merged.

BatchScopeHow behaviour was proved unchanged
1Toolkit (CardForge runtime)Every portable suite with identical counts, the Unity rehearsal, the LAN and local-authority network pairs
2Tools (relay, trusted authority, Studio, check suites, benchmark)Byte-identical suite logs and API responses against a copy of main; the game assembly hash unchanged
3Game runtime logicIL comparison (only refactored members changed); scratch Unity editor probes that dumped every generated scenery object and every room validation on main and on the branch, byte-identical; the rehearsal's PASS templates
4Game UI (hosted windows, journal, deck builder, Waybook, DuelUi)Five editor probes (navigation, glyphs and hints, dialogue presenter, colours and border meshes, settings), byte-identical; screenshots within run-to-run variation
5Editor build codeThe key-free stages of the private-pair build script, identical output; shipping players identical apart from build identity; shipping assembly IL identical
6QA test codeEach assertion's condition and message unchanged; the rehearsal's ordered PASS sequence identical to main's
7Tools check programs written as top-level statements, which the first six batches did not measureByte-identical suite logs against a copy of main

The techniques were the same throughout: guard clauses, one named step per logical block called in the original order, small predicates for long &&/|| chains, lookup tables for long switches of pure values, and, in the QA rehearsal, helper iterators that the runner executes inline so no frame timing changes (see QA & Rehearsals). Helpers carry their parent's name as a prefix, which is why many method names are long.

The pull requests record the per-batch evidence in full: the complexity pull requests.

A class whose summed CC is in the thousands, spread over several hundred members and many partial files, is hard to change safely for reasons the per-member number cannot see. Every partial file can read and write every field, the rehearsals reach hundreds of its members directly, and nothing in it can be tested without the scene. Splitting such a class along real seams (a plain model the view binds to, one class per screen, a separate loader) is a different kind of work from the batches above: it changes structure, not just method boundaries. The candidates and their options are F01 IsometricSlice, F02 ExpeditionView, F21 CircuitSliceChecks and F22 IsometricSliceBuild.

08What the numbers do not say

  • Not coupling. How many other types a class reaches, string-keyed reflection, and production code calling QA code are not measured here; see Findings.
  • Not duplication. Two parallel implementations of the same idea each score low.
  • Not correctness. Low complexity makes a member easier to test; it does not test it.
  • Not every build configuration. Code compiled only for players or for Android is outside the measured symbol set (§01).

09Keeping it below 10

Run the analyzer with a limit; it lists every member above it and exits 1:

dotnet run --project Tools/CodeMetrics/CodeMetrics.csproj -c Release --artifacts-path Temp/CodeMetrics -- --root . --out Temp/CodeMetrics/metrics.json --max 9

It is not part of Tools/Run-Checks.ps1. Making it a required check, and whether test and editor code are held to the same limit as player code, are owner decisions tracked in the roadmap's open owner decisions. Until then, a member that reaches 10 shows up in the Now table the next time this wiki is built.
