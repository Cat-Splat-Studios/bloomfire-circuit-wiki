What the game remembers

The three things the game writes to disk (Circuit progress, player settings and opt-in playtest reports), how each is written and recovered, and what is deliberately never saved.

In 60 seconds

  • Three writers, no more. In Game/EmberGrove/Assets/Runtime and the toolkit's Runtime folders, the only file or PlayerPrefs writes are CircuitPersistence.Save, ExpeditionApp.SavePreferences and PlaytestSessionService.Persist. QA builds add the testing-save preferences and reset folder in CircuitSliceChecks.Saves.
  • Progress is one JSON file. CircuitSave (wrapper version 5) holds the whole CircuitState plus a few presentation fields, in bloomfire-circuit-v2.json under Application.persistentDataPath.
  • Restore tries four files in order: the primary, its .previous, the legacy bloomfire-circuit-v1.json, its .previous. Unreadable files are kept and copied aside as *.corrupt-<UTC>-<guid>; a file from a newer game blocks every write.
  • Writes are atomic. A save goes to *.tmp, is flushed to disk, then File.Replace swaps it in and rotates the old file to .previous.
  • Settings are PlayerPrefs, not files. PlayerSettings is JSON under the key EmberGrove.PlayerSettings.v1; rehearsals get their own keys with a .qa.<hash> suffix. A battle's CombatState and every network session live only in memory.

Before you start

  • The rules of the saved state itself (schema versions, migrations, what CircuitRules.Recover repairs) belong to the toolkit's Circuit saves and recovery and to MAINTAINING's deck upgrades and world layouts sections. This page covers the file layer around them.
  • Where those folders and keys are on each operating system is in MAINTAINING's internal preview candidate section; backing up player data is in Backup and restore.
  • How CircuitState changes through ApplyCircuit is on World & Journal.

03The CircuitSave wrapper and its versions

CircuitSave is a serializable class around the toolkit's CircuitState. Its own Version is separate from the profile and run versions nested inside the state; all of them are checked on restore.

FieldMeaning
VersionThe wrapper version. CaptureCircuitSave writes 5; RecoverCandidate accepts 1–5. It has no default, so a file without one reads as 0 and is rejected.
StateThe complete CircuitState (profile and run)
HasWorldPosition, WorldX, WorldZ, FocusStageWhere the traveller stood, relative to the district at FocusStage. Used only when Version >= 2, a run exists and the numbers are finite.
Zoom, FollowCamera, ReducedMotionCamera and motion choices. Zoom is clamped to 0.7–1.5 on restore.
WelcomeSeen, PracticeCompleted, OpeningBeatId, CompletedLessonIds, ReadLessonIdsOnboarding and lesson progress that lives outside CircuitState
ClubNickname, ClubBadgeIdLocal presentation only; never used as a review or session identity

A save is "from a newer game" (SavedByNewerVersion) when the wrapper version is above 5, or the profile, run or world-layout version is above CircuitRules.CurrentProfileVersion, CurrentRunVersion or CurrentWorldLayoutVersion, or CircuitRules.HasNewerRoomRevision is true for the run. Older nested versions are upgraded in memory by CircuitRules.Recover; reading never rewrites the file, and the next ordinary save keeps the old bytes as .previous. The per-version behaviour is owned by the guides linked under Before you start.

04File names and folders

CircuitPersistence is constructed with two paths, the primary and the legacy file, and derives every other name from them.

NameRole
bloomfire-circuit-v2.jsonThe primary save (CircuitPath)
bloomfire-circuit-v2.json.previousThe file the last save replaced
bloomfire-circuit-v2.json.tmpA save being written; replaced into the primary when complete
bloomfire-circuit-v1.json and .previousThe legacy save (PreviousCircuitPath). Read as a fallback; the game never writes or deletes it (only the QA testing reset below moves one).
<rejected file>.corrupt-<yyyyMMddTHHmmssfffZ>-<guid>A copy of each file restore could not read, made before the next save. Nothing deletes these.

Which folder (CircuitStorageRoot)

  • Players: Application.persistentDataPath. These file names are frozen identifiers (product names).
  • QA testing save (UNITY_EDITOR or CIRCUIT_QA only, when CircuitSliceChecks.TestingAllCards): the subfolder testing-all-cards. SaveCircuit refuses to write anywhere else while it is on (InTestingFolder).
  • Lifecycle and story rehearsals: CircuitSliceChecks.LifecycleSaveDirectory, which is <-circuit-verify output>/saves (or a story folder inside that output) and throws if it would land inside the player's persistentDataPath.
  • Other rehearsals (-circuit-verify or -expedition-net-verify without a lifecycle folder): CircuitSavesSuppressed is true, so restore is skipped and SaveCircuit returns success without writing.

Starting the testing save again from Settings sets TestingResetWanted; on the next start CircuitSliceChecks.ApplyTestingReset moves its four save files into a reset-<UTC> folder beside them. Nothing is deleted.

05Restoring: the candidate order

CircuitPersistence.Restore(definition, deserialize, warning, out restoredPath) walks four candidates in a fixed order. The first usable one wins, but it keeps reading the rest so that a newer-version file anywhere still blocks writes.

stateDiagram-v2
  direction TB
  state "Next candidate" as Next
  state "Read and deserialize" as Read
  state "RecoverCandidate" as Recover
  state "Rejected, path kept in rejectedPaths" as Rejected
  state "WriteBlockReason set" as Blocked
  state "Restored" as Restored
  [*] --> Next
  Next --> Next: file missing
  Next --> Read: file exists
  Read --> Blocked: SavedByNewerVersion
  Read --> Next: a save is already restored
  Read --> Recover: nothing restored yet
  Read --> Rejected: empty or malformed, nothing restored yet
  Recover --> Restored: version 1 to 5, collection present, CircuitRules.Recover ok
  Recover --> Rejected: any check fails
  Blocked --> Next
  Rejected --> Next
  Restored --> Next: keep checking for newer files
  Next --> [*]: all four inspected
  note right of Next
    v2.json, v2.json.previous,
    v1.json, v1.json.previous
  end note

One pass of CircuitPersistence.Restore. "Rejected" covers IOException, InvalidDataException, UnauthorizedAccessException, ArgumentException (Unity's malformed JSON) and FormatException. If the rejected file is the primary, preservePrevious is set so the next save does not rotate it over the good backup.

Then IsometricSlice.RestoreCircuit finishes the job:

  1. Use what was restored. RestoreCircuitSaved copies the state and the wrapper fields, and sets a notice: restored from a .previous or after a rejection ("restored from an earlier save"), decks repaired, nothing readable ("could not be read… original files will be kept"), or the WriteBlockReason text, which wins.
  2. Fill gaps. No profile → CircuitRules.NewProfile. No run → RestoreCircuitStartRun (the first playable saved deck, else the initial starter).
  3. Close an interrupted match. A saved Run.PendingDuel is resolved as CircuitDuelOutcome.Interrupted: the player is back at the challenge and no result is invented.
  4. QA only. RestoreCircuitTesting tops up the testing save with every card and records TestingSaveSummary for the Settings screen.
The save is read only after the content pack has loaded and a CircuitDefinition exists, because Recover needs the definition. A pack that fails to load leaves the save untouched (content.html §02).

06Saving: tmp, Replace, .previous

Most saves start in ApplyCircuit, which swaps in a new CircuitState from a CircuitRules call and then calls SaveCircuit. With requireSaved: true a failed write puts the previous state back so the player can retry.

sequenceDiagram
  participant S as IsometricSlice
  participant R as CircuitRules
  participant P as CircuitPersistence
  participant D as Save folder
  S->>R: e.g. CommitEvent(...)
  R-->>S: Result<CircuitState>
  S->>S: ApplyCircuit(result, requireSaved: true)
  S->>S: SaveCircuit checks lobby, suppression, testing folder and Ready
  S->>S: CaptureCircuitSave() writes Version 5
  S->>P: Save(JsonUtility.ToJson(save, true))
  alt WriteBlockReason is set
    P-->>S: throw IOException
  else ordinary save
    P->>D: File.Copy each rejected file to .corrupt-UTC-guid
    P->>D: write v2.json.tmp, Flush(true)
    P->>D: File.Replace(tmp, v2.json, v2.json.previous)
    Note over P,D: File.Move when v2.json is new, and no backup on the first save after a rejected primary
    P-->>S: return
  end
  S->>S: on IOException or UnauthorizedAccessException set circuitNotice
  S->>S: requireSaved and failed, so restore the previous state

One save from a player choice. SaveCircuitWrite catches only I/O and access errors; anything else propagates.

When the game saves

TriggerCode
Rule changes: events, visits, new runs, episode results, deck builder changesApplyCircuit (several with requireSaved: true; new runs also with restoreAtArrival, which saves no position so a failed rebuild resumes at arrival)
Before and after a matchPlayCircuitDuel: ApplyCircuit(BeginDuel…) saves the PendingDuel, then ApplyCircuit(ResolveDuel…) commits the outcome before the return animation
Presentation choicesDirect SaveCircuit() calls for camera, motion, zoom, lessons read, the onboarding badge and nickname, returning to the title page and returning from the settings session; OpenModal also calls SaveProgress whenever a window opens outside the title page
Leaving the appOnApplicationPause(true), OnApplicationQuit and OnDestroy call SaveProgress; the Quit page calls SaveBeforeQuit and asks again if it fails
NeverWhile a Versus lobby is open (LobbyActive): SaveCircuit returns true without writing
Why rejected files are copied, not moved

A rejected file may be the only copy of real progress that a later fix could read. Save copies every rejected candidate to a .corrupt- name before it replaces anything, and stops the whole write if a copy fails, leaving the originals and the good backup in place; the next attempt retries the copies. On the first save after a rejected primary, File.Replace is called with no backup name, so the corrupt bytes do not overwrite the usable .previous; later saves rotate normally.

07Testing the save code: the portable build

Because CircuitPersistence has no Unity dependency, the same source file is compiled into a plain .NET program and exercised with real temporary files.

Portable runner

Tools/CircuitPersistenceChecks/CircuitPersistenceChecks.csproj compiles Result.cs, the toolkit's Core and Circuit folders, CircuitPersistence.cs and CircuitPersistenceVerification.cs with CIRCUIT_PERSISTENCE_PORTABLE. Program.cs supplies a System.Text.Json SaveCodec that turns JsonException into ArgumentException, as Unity does. Run it as the Persistence suite of Tools/Run-Checks.ps1.

Unity runner

CircuitPersistenceVerification.RunBatch runs the same RunScenarios list with JsonUtility in a batch-mode editor, writing its report and fixtures under Temp/ReleaseReview. A few scenarios run in only one runner (if (native)).

The whole verification file is wrapped in #if UNITY_EDITOR || CIRCUIT_PERSISTENCE_PORTABLE, so no player compiles it. Lifecycle behaviour around real process exits (unload, quit during a battle, quit on a result, resume) is rehearsed separately by CircuitSliceChecks.Saves with -circuit-lifecycle; see QA & Rehearsals. What the scenarios cover and how to run them is in the Circuit save recovery checks README.

08Player settings

PlayerSettings is a flat serializable class of presentation preferences (volumes, mute, motion, contrast, text size and speed, subtitles, spoken help, input options, frame limit, window size and mode, performance). Its own comment is the rule: no setting takes part in combat or network state.

PieceBehaviour
PlayerSettings.VersionAlways 1; Normalize sets it
PlayerSettingsRules.NormalizeClamps every float to its range (NaN or infinity becomes the default), resets FrameLimit to 60 unless it is 30, 60, 90 or 120, resets unknown enum values, and zeroes a window size outside 640×480 to 16384×16384. Every read and write goes through it.
EmberGrove.PlayerSettings.v1The PlayerPrefs string holding the JSON. ReadPreferences ignores a value of 8192 characters or more, and returns defaults if parsing throws ArgumentException.
EmberGrove.Muted, EmberGrove.ReducedMotionLegacy int keys. Read only when the JSON key is empty; always written alongside it.
PreferenceKey(key)With -expedition-net-verify <path> or -circuit-verify <path>, appends .qa. and a 16-digit hex FNV-1a hash of the full path, so each rehearsal output gets its own keys. Rehearsals also read Muted as true.
SavingChangeSettings applies at once and marks the settings dirty; TickSettings saves after SettingsSaveDelay (0.35 s). Closing Settings saves at once; FlushSettings saves pending changes on pause, quit and destroy, and when the world releases a hosted session (IsometricCombatBridge.ReleaseSettings).
Display trialPreviewDisplay changes resolution for 15 s; until ConfirmDisplay, SaveSettings writes the previous size and mode. ResetPreferences keeps the display size and mode.

Two owners, one store. Hosted sessions hold an ExpeditionApp.Settings instance; the world calls the static ReadPreferences, SavePreferences and ApplyRuntimePreferences from IsometricSlice.Preferences. ApplyRuntimePreferences sets High Contrast in DuelUi.MenuColour, AudioListener.volume, the quality level and the frame rate. On a first run with no settings key, LoadWorldPreferences folds the world save's ReducedMotion into settings once and saves them; after that the settings value wins, although CircuitSave still writes its own ReducedMotion field.

QA builds add two more keys through PreferenceKey: Bloomfire.Testing.AllCards and Bloomfire.Testing.AllCards.Reset (CircuitSliceChecks.Saves). Where PlayerPrefs live on each platform, and why moving the save folder does not reset them, is in internal preview candidate.

09Playtest reports

PlaytestSessionService records nothing until a player presses START LOCAL PLAYTEST in the feedback panel drawn by ExpeditionView.Journey.cs or ExpeditionView.PortraitJourney.cs. Each ExpeditionApp creates its own service: PrepareTable makes one for a table session, and Start makes one if none exists.

  • File. persistentDataPath/Playtests/playtest-<guid>.json, a PlaytestReport with SchemaVersion = 1, stamped with Application.version and Application.productName.
  • Write. Persist writes a unique .tmp-<guid> file, flushes it, then File.Replace with no backup (or File.Move the first time), and always deletes the temporary file.
  • Checkpoints. On start, every 20 actions, every match start, end or abandonment, each feedback form and stop. Stop runs on OnApplicationQuit and when a session finishes.
  • Bounds. MaxEvents, MaxFeedbackEntries and MaxFeedbackLength; events past the limit are counted in DroppedEvents. Free text is trimmed and common e-mail and IP address patterns are redacted.

Rehearsals construct the service with their own output folder. The report fields and the full bounds are owned by local playtest recording.

10What is never saved

Some state is deliberately memory-only, so that a crash or quit can never leave a half-played match or a stale connection on disk.

StateLives inAfter a restart
CombatState (a battle in progress)ExpeditionApp.State; on a host or trusted service, ExpeditionAuthorityThe saved PendingDuel is resolved as Interrupted; the challenge can be played again (§05)
Network sessions, lobbies and their messagesExpeditionNetworkSession and the Versus lobby sessionGone; the toolkit's runtime code writes no files at all. See Networking.
Adventure progress made inside a Versus lobbyNot recordedSaveCircuit skips writing while LobbyActive
The loaded content pack and decoded mediaLoadedContentPack, CardArtworkCacheReloaded from the pack root
The legal-action cache, open pages and navigation historyExpeditionApp, IsometricSlice (circuitBackStack)The title page opens; the traveller's position comes from the save

11Backups and moving between versions

The game keeps one rolling backup and every rejected file; anything older is the player's own backup.

  • Downgrades are blocked, not merged. Opening an older build on a newer save shows the WriteBlockReason notice and refuses every write, even if an older compatible candidate could be displayed. Continue with the newer game.
  • Upgrades happen in memory. The next ordinary save writes the new version and leaves the old bytes as .previous; the legacy v1 file is never touched.
  • Git does not hold player data. Saves, preferences and playtest reports must be backed up separately; see release artifacts and player data.
  • One account, one profile. A different content pack folder does not create a separate save (updating an installed game).
