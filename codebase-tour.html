The Codebase Tour

A guided walk through the repository and its build units: what each folder, assembly and .NET project owns, how the Unity project is laid out, which big classes are split into partial files, and how content reaches a player.

In 60 seconds

  • Six source owners. Game, Toolkit, Content, Tools, Docs and Teaching sit at the root. Builds and Temp sit beside them and are ignored by git. See §01.
  • The toolkit is a Unity package with seven runtime assemblies. Every one except CardForge.Content is free of the Unity engine. The game pulls the package in through a file: entry in its package manifest. See §02.
  • The game has no assembly definitions. Assets/Runtime, Assets/Runtime/Exploration and Assets/Tests all compile into Assembly-CSharp, and only the folders named Editor (Assets/Editor and Assets/Tests/Editor) go elsewhere. QA code stays out of shipping players through #if guards, not through assemblies. See §04.
  • Four big classes are split by concern. IsometricSlice, ExpeditionView, ExpeditionApp and CircuitSliceChecks are each split into many Type.Concern.cs partial files, and the suffix tells you the concern. See §06.
  • Names are kept for compatibility. One namespace spans four assemblies, and the "Expedition" and "Isometric" names survive from earlier products. Read §07 before you go looking for a type by its namespace.

Before you start

  • You do not need Unity for this page. It describes files on main only.
  • Keep the source map open beside this page. It gives each layer's path and responsibility in one table, and this tour does not copy it.
  • For the three layers and one player action drawn end to end, see the home page §01 and §02. If a term is new to you, look it up in the glossary.

Every runtime assembly except CardForge.Content sets noEngineReferences. Combat, adventure, lesson, navigation and networking rules therefore cannot touch Unity types, which is what lets the .NET tools compile them unchanged (§05). CardForge.Content uses JsonUtility, UnityWebRequest and the Application paths. The relay, Content Studio and the Content and FieldSetup suites compile its files with CARDFORGE_HEADLESS (Builds §04). Without the symbol, ExpeditionContent.cs calls JsonUtility. The manifest parsing in ContentPackFiles.cs and Content Studio's own Program.cs call it with or without the symbol. So Content Studio and the Lessons, WorldFacts and Performance suites add a UnityEngine stand-in (§05).
Why each assembly lists its references explicitly

AGENTS.md requires an assembly to reference directly every assembly whose types it uses, and never to rely on an indirect reference. The example it gives is EmberGrove.Result<T> from CardForge.Functional. The retired root project broke exactly this way, and Teaching/LegacyEditor/EmberGrove.Networking.asmdef is kept as the corrected manifest (Teaching, Legacy editor assembly correction).

The file-by-file table for the package is in the toolkit's ARCHITECTURE, File responsibilities. What the package promises a consumer is in the package boundary. The class diagrams are on Diagrams.

The guards are the only thing keeping QA code out of a player. Moving a harness into an Editor folder would take it out of the QA players that need it, and putting it under an .asmdef would cut it off from the internal members it checks. 08Where content lives and how it reaches a player

Authored data lives in Content/ and nowhere else. The build copies it into the ignored StreamingAssets, and the game reads it from there at run time. Models, animations, materials and levels are different: they stay in the Unity project as assets.

  1. Authoring. Designers edit a working copy of the pack in CardForge Content Studio, and a maintainer brings the export into Content/ (Receive a creator delivery). Lessons can also be edited in Tools/CircuitStudio/lessons.html, and dialogue branches simulated in its index.html.
  2. Staging. StageEncounterContent parses and validates the manifest, combat, media and dialogue, checks that every media file exists, and then copies the pack. StageCircuit validates lessons.json against the real catalog and copies the sidecars and voice files. StageSector validates and copies sector.json.
  3. Loading. ContentPackFiles.Load reads the manifest and its documents, with a size limit on each JSON file, and validates them. It hashes the combat JSON into ActiveCombatHash and returns a LoadedContentPack. IsometricSlice.LoadCircuit then builds the CircuitDefinition from the sidecars and the pack, and checks every rival deck.
  4. Again for every session. Each hosted ExpeditionApp loads the pack itself in Start, from the root it was given, and builds its own Catalog.

The pack format is defined in PACK_CONTRACT.md, and the designer workflow in the authoring guide. The loading boundary is described in External content and media. Content & Media goes further into media, art leases and audio.

09A reading order

One way into the code for a programmer who knows Unity and C#. Each step leaves you able to read the next one.

  1. The rule shape. Read Toolkit/…/Runtime/Functional/Result.cs, then Functional composition and the small monad. Everything else returns a Result<T>.
  2. One match. Read Runtime/Core/CombatContracts.cs for the types, then CombatRules.NewMatch, LegalCommands and Resolve in CombatRules.cs. See Rules Engine.
  3. The adventure's rules. Read Runtime/Circuit/CircuitDefinition.cs from CircuitProfile down to CircuitState, then the Circuit rules README.
  4. The world that uses them. In Game/EmberGrove/Assets/Runtime/Exploration, read IsometricSlice.cs (Start), then in IsometricSlice.Circuit.cs read LoadCircuit, ApplyCircuit and PlayCircuitDuel. See World & Journal.
  5. The battle it hosts. Read IsometricCombatBridge.cs, then ExpeditionApp.cs and ExpeditionApp.Session.cs. See Hosted Sessions.
  6. The screens. Read ExpeditionView.cs and ExpeditionView.Navigation.cs, then IsometricSlice.WaybookMenu.cs for the title page. See UI & Menus.
  7. The network. Read Runtime/Networking/NetworkContracts.cs, ExpeditionAuthority.cs and then ExpeditionNetworkSession.cs. See Networking.
  8. How it is checked. Read the Tests README and the tools README, then QA & Rehearsals and Builds & Tools.
  9. What to fix. Read Findings, with Complexity and Diagrams beside it.
