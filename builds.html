How a build is made

The Unity build owner IsometricSliceBuild, the defines it sets, the identity files it writes and the PowerShell scripts that turn players into checked packages. Also the other tools in Tools/, and which file owns each version number.

In 60 seconds

  • One build owner. Every player build goes through one private method, IsometricSliceBuild.Build(rehearsal, target), in Assets/Editor. The menu items and the batch -executeMethod entries are thin wrappers around it (§02, §03).
  • QA is a define, not a scene. A rehearsal build is the same scene and content with CIRCUIT_QA added through extraScriptingDefines. -expedition-network-qa also adds EMBERGROVE_QA. The project-wide defines contain neither (§04).
  • Every build leaves an identity. build-report.txt and build-info.json sit beside the player. The JSON records the version, build GUID and the hash of Assembly-CSharp.dll, which the rehearsal report and the packager must match (§05).
  • A candidate is proved before it is packaged. Tools/Package-Isometric.ps1 snapshots the source, then in a second run requires fresh shipping and QA builds and a passing rehearsal of that exact QA build, runs Validate-CircuitPlayer.ps1 on both, and only then writes the ZIP and its sidecars (§06).
  • The editor owns the product version. bundleVersion in ProjectSettings.asset (Player Settings › Version) is the product version. A candidate passes its own label, and the build puts the old value back afterwards (§10).

Before you start

This page explains structure. The step-by-step procedures, the command lines and the current evidence are in MAINTAINING § Verify and build the game and the sections after it. What the rehearsal does once it is built is on QA & Rehearsals.

03Inside Build()

Every player build runs the same steps: validate, stage content, snapshot the editor's settings, override them for the build, build, write the identity, and restore the settings in a finally.

flowchart TD
  entry["menu item or -executeMethod"] --> build["Build(rehearsal, target)"]
  build --> relay["PrivateRelayQaRequest: null unless a private pair asked for it"]
  relay --> isAndroid{"Android target?"}
  isAndroid -->|yes| droid["ValidateAndroidPrerequisites, version code, ABI, AndroidContentIdentity"]
  isAndroid -->|no| out
  droid --> out["BuildOutput: default folder, or a fresh -circuit-build-output"]
  out --> scene["ValidateBuildScene(CircuitJourney.unity)"]
  scene --> stage["StageSector, StageEncounterContent, StageCircuit"]
  stage --> snap["new BuildPreferences(target)"]
  snap --> set["set product, company, bundleVersion, backend, render pipeline"]
  set --> inst["PrivateRelayQaScope.Install, private pair only"]
  inst --> player["BuildPipeline.BuildPlayer with extraScriptingDefines"]
  player --> files[("build-report.txt and build-info.json")]
  files --> fin["finally: dispose the private scope, previous.Restore()"]

The order of Build(). A failure at any step throws. Once BuildPreferences has taken its snapshot, the finally restores the editor's player settings and the exact bytes of the three settings files.

  • Staging. Content moves from the repository into the ignored Assets/StreamingAssets. StageSector validates and copies Content/Exploration/sector.json. StageEncounterContent validates the default pack and copies Content/EmberGroveDefault into StreamingAssets/Content. StageCircuit validates lessons.json and copies the Circuit sidecars and voice files. How the game reads them back is on Content & Media.
  • Overrides. The build sets the product name to "Bloomfire Circuit", or "Bloomfire Circuit QA" for an Android rehearsal. It also sets the company "Cat Splat Studios", the version, the window defaults (3840×2160 fullscreen on the Mac, a 1600×900 window on Windows), Mono for desktop and IL2CPP ARM64 for Android, low managed stripping, and the Circuit world render pipeline. BuildPreferences captured all of these first. It also keeps the raw bytes of the three settings files, because BuildPlayer writes overrides to disk.
  • Build options. LZ4HC compression and a detailed build report always. Android adds Development. Android and private builds add CleanBuildCache, so a cached scene override cannot leak into a later baseline.
  • Output. With no candidate arguments, a desktop build goes to Builds/CircuitJourney, CircuitJourneyQA, CircuitJourneyMac or CircuitJourneyMacQA, under the stem BloomfireCircuit. Android always needs both -circuit-build-output and -circuit-build-version. A candidate output must be a new or empty folder under Builds or Temp that does not pass through a linked directory.

04Compile-time defines

The QA defines never appear in ProjectSettings.asset; its Standalone defines are SENTIS_ANALYTICS_ENABLED;APP_UI_EDITOR_ONLY, and its Android defines are empty. Build() passes them per build through BuildPlayerOptions.extraScriptingDefines, so an editor session and every ordinary build compile without them.

Unity's own UNITY_EDITOR also turns on the rehearsal and harness code, because their guards read UNITY_EDITOR || …; that is why the rehearsals run in Play Mode. The private-relay blocks are the exception: they require !UNITY_EDITOR. UNITY_ANDROID is compiled correctly only when Android is the active target before the build starts, which is why Build() refuses an Android build from another active target.

05build-info.json and its sidecars

After BuildPlayer returns, Build() writes two files beside the player, whether the build passed or failed. Both scripts identify a build by the GUID and hashes in these files.

build-report.txt

One line: the result, total size, errors, warnings and time. Package-Isometric.ps1 accepts only a report that starts with Succeeded: and contains , 0 errors,.

build-info.json (BuildIdentity, schema 1)

What was built: Version, Rehearsal, Scene, Platform, Architecture, Development, ApplicationId, UnityVersion, Backend, graphics APIs and MSAA. Proof: BuildGuid, Result, Errors, Warnings, StartedUtc and CompletedUtc, AssemblySha256 (desktop) or ArtifactSha256 (Android APK). Android content identity: ContentSha256, Fingerprint, ContentVersion, Protocol, RulesVersion and NetworkRulesVersion, plus the version code and API levels.

Three pieces depend on them. The rehearsal writes its own BuildGuid, AssemblySha256 and Version into verification.txt for comparison (qa.html §06). Validate-CircuitPlayer.ps1 refuses to run when Platform or Architecture differ from what was asked; a Mac player needs build-info.json to exist at all. Package-Isometric.ps1 ties the three together, as the next section shows.

The packager adds more files at each stage:

WhereFileWritten by
Evidence directorysource-snapshot.json-PrepareReviewEvidence: the SHA-256 of every non-ignored file under Game/EmberGrove, Toolkit/Packages and Content, plus the packager and validator scripts (uncommitted edits included), with the HEAD revision
Evidence directorycandidate-evidence.json, production-assembly-validation.json, rehearsal-assembly-validation.json-ReviewCandidate, only after every check passed
Inside the ZIPSTART_GAME.cmd or START_GAME.command, START_HERE.txt, CREDITS.txt, CANDIDATE.json, Licenses/, Provenance/, MANIFEST.sha256-ReviewCandidate; the manifest covers every other file in the payload
Beside the ZIP<zip>.sha256, <zip>.manifest.sha256, <zip>.validation.json-ReviewCandidate, after reading the ZIP back and re-hashing every entry

06The candidate pipeline

An internal preview candidate is one platform's shipping player, packaged only after a QA build from the same source passed a rehearsal. Package-Isometric.ps1 runs in two separate invocations, before and after the builds. The second one refuses anything stale, mismatched or changed.

flowchart TD
  prep["Package-Isometric.ps1 -PrepareReviewEvidence"] --> snap[("source-snapshot.json")]
  prep -.-> checks["Run-Checks.ps1, run by the maintainer, not read by the packager"]
  snap -->|started after the snapshot| qa["CircuitRehearsal build, CIRCUIT_QA"]
  snap -->|started after the snapshot| ship["CircuitWindows build, no QA define"]
  qa --> qainfo[("QA build-info.json and build-report.txt")]
  ship --> shipinfo[("shipping build-info.json and build-report.txt")]
  qa --> run["QA player -batchmode -circuit-verify dir"]
  run --> ver[("verification.txt and captures")]
  snap & qainfo & shipinfo & ver --> review["Package-Isometric.ps1 -ReviewCandidate"]
  review --> gate{"source unchanged, builds fresh, hashes and identities match?"}
  gate -->|no| stop["throw, no ZIP or evidence written"]
  gate -->|yes| val["Validate-CircuitPlayer.ps1 on the shipping and the QA player"]
  val --> content["StreamingAssets equals canonical Content in both players and the payload"]
  content --> zip[("ZIP and its three sidecars")]
  content --> evid[("candidate-evidence.json and both assembly reports")]

The Windows candidate. The Mac candidate is the same sequence run on the Mac, using CircuitMacRehearsal and CircuitMac and passing -Platform macOS -Architecture x86_64 to both packager steps.

What -ReviewCandidate checks before it writes the archive or any evidence, in order:

  1. Same source. The current file hashes must equal source-snapshot.json. They are checked again after the ZIP is built, so an edit during packaging also fails.
  2. Fresh, separate builds. Both players must have a successful build-info.json that started after the snapshot. They must disagree on Rehearsal and agree on Version, and each AssemblySha256 must equal the hash of the DLL now on disk. The shipping build folder must not end in QA.
  3. The rehearsal ran this QA build. verification.txt must start with PASS Bloomfire circuit rehearsal and be written after the QA build finished. Its BuildGuid, AssemblySha256 and Version lines must equal the QA build-info.json.
  4. The assembly contract. Validate-CircuitPlayer.ps1 runs against both players (§07).
  5. Exact content. Every file under each player's StreamingAssets, and under the payload copy, must hash-match the canonical Content/ set, with nothing extra and nothing missing.

The commands, the batch method table and the Mac launch flags are owned by MAINTAINING § Internal preview candidate. Which candidates exist and what they were cleared for is in the roadmap.

08Android builds

Android uses the same Build(), with more checks before and a strict rule around the active platform. Switching Unity to Android rewrites settings and defines, so the original state is captured first and restored by a separate editor run.

  1. Capture with CircuitAndroidCaptureBuildState while the original target is active.
  2. Check with CircuitAndroidPreparationChecks. For a private pair, also run CircuitPrivateRelayQaPreparationChecks.
  3. Build with -buildTarget Android, using CircuitAndroidDevelopment or CircuitAndroidRehearsal. Both need an explicit -circuit-build-output, version label and -circuit-android-version-code, and -circuit-android-abi arm64 is required. -circuit-android-graphics-api gles3 and -circuit-android-msaa 1 are optional, and MSAA is allowed only with GLES3. The content identity (AndroidContentIdentity) is computed before staging and compared with the staged combat file after it. The version label must satisfy the pack manifest's MinimumGameVersion; only the Android build path checks this.
  4. Restore with CircuitAndroidRestoreBuildState and the recorded original -buildTarget, after success or failure.

Only an Android rehearsal sets AndroidNetworkQaBuild. During that build AndroidNetworkQaLinker (an IUnityLinkerProcessor) writes a link.xml preserving all of Assembly-CSharp. It was added when the harness reached members by name; since F08 it calls them directly, so the descriptor is a conservative guard, and removing it needs a passing Android QA rehearsal without it. An ordinary Android build registers nothing. The reasons for the GLES3 and MSAA options, and the APK inspection list, are in MAINTAINING § Android development build.

09The private relay pair and its guard

The private QA players carry a tester access key for one hosted relay, so the code around them is built to keep that key out of command lines, logs, source control and every other build. Two pieces do this: an orchestration script that alone may supply the key, and a build guard that runs for every Unity build.

flowchart TD
  pre["preconditions: Windows, STA, the pinned Unity editor, unexpired window, a network-qa version label, no generated residue, no editor or game process running, one workflow at a time"] --> s1
  s1["01 CircuitAndroidCaptureBuildState"] --> s2["02 CircuitAndroidPreparationChecks"]
  s2 --> s3["03 CircuitPrivateRelayQaPreparationChecks"]
  s3 --> s4["04 CircuitWindows: ordinary control build"]
  s4 --> key["masked dialog: Request-ExistingKey, then Confirm-ExistingAccess"]
  key --> s5["05 CircuitRehearsal: private Windows-QA"]
  s5 --> s6["06 CircuitAndroidRehearsal: private Android-QA"]
  s6 --> s7["07 CircuitWindows: control after private"]
  s7 --> fin["finally: Remove-OwnedInjection, 08 CircuitAndroidRestoreBuildState, Sanitize-OwnedLogs"]
  fin --> pres[("build-preservation.json")]

Tools/Build-PrivateNetworkPair.ps1. Every stage is a separate batch editor (Run-Unity) with its own log under the evidence folder. After stages 04, 05 and 07, Assert-PrivateAssembly reads the Windows player with Cecil. The pass needs all eight stages to pass and every source hash to be unchanged.

  • Key path. The key comes only from the masked Bloomfire private QA builds dialog. Only the two private stages receive it, through the environment variable BLOOMFIRE_PRIVATE_QA_RELAY_KEY, together with a fresh -expedition-private-relay-owner GUID. PrivateRelayQaRequest validates it, then clears the variable in the editor process so compiler children do not inherit it. PrivateRelayQaScope.Install writes the ignored Assets/Tests/Runtime/PrivateRelayQaSettings.generated.cs and its .meta just before BuildPlayer; Dispose deletes exactly those bytes. An -expedition-private-relay-adopt form reuses generated bytes that are already in place, without the variable.
  • Guard. PrivateRelayQaBuildGuard is an IPreprocessBuildWithReport with callbackOrder int.MinValue, so it runs before any build, including the generic Unity Build menu. It fails the build in four cases. The first is EMBERGROVE_PRIVATE_RELAY_QA sitting in the project-wide defines. The second is an unauthorised build that sees a private flag, the key variable or the generated file. The third is an authorised build that lacks the generated file, still sees the key variable, or repeats or omits a required flag. The fourth is an authorised build whose platform, output path, bundleVersion or generated bytes differ from the scope it was given.
  • Assembly checks. Assert-PrivateAssembly requires that the private player has ExpeditionApp.PrivateRelayQaActive and the ordinary controls do not. An ordinary player must not contain the PrivateRelayQaSettings type. Once the key is known, the check also requires the key literal to appear in the private player and in neither control.
  • Expiry. Each private build has a fixed expiry. The same endpoint and expiry are written three times: as constants in IsometricSliceBuild.cs (PrivateRelayQaEndpoint, PrivateRelayQaExpiry), in ExpeditionApp.Network.cs, and as variables in Build-PrivateNetworkPair.ps1. A new test window means editing all three.

-CheckPreflight runs only the script's fixture tests of its relay access preflight, in memory and over loopback. It uses no key, no external service and no Unity, and it is the RelayPreflight check suite. The owner-facing procedure and the record of each private pair are in MAINTAINING § Android development build; the two-device test is in NETWORKING § Private QA two-device test.

11The other tools

Everything else in Tools/ is either a check suite (qa.html §02) or one of the authoring and delivery tools below. Each tool's README owns its commands; Tools/README § Find the right tool maps tasks to entry points.

ExpeditionRelay and its launcher

ExpeditionRelay.csproj is an ASP.NET Core web project (with CARDFORGE_HEADLESS). It compiles the toolkit's core, progression, authority and contracts and adds RelayApplication, RelayRuntime and TrustedMatchApplication. Launcher/EmberGroveRelay.csproj wraps it in a WinForms app, EmberGroveRelay.exe. Publish-Relay.ps1 publishes that app self-contained, single-file and untrimmed for win-x64, or with -Target ContainerSource copies the relay source with Dockerfile and render.yaml and writes source-manifest.json, uploading nothing. Package-Relay.ps1 zips the published folder with a manifest, and Test-Launcher.ps1 is the RelayLauncher suite. Relay README

ContentStudio

One ContentStudio.csproj compiles the toolkit's functional, core, progression, circuit and content sources, using UnityBoundary.cs in place of UnityEngine. By default it is a local web service, EmberGrove.ContentStudio, that the Studio suite tests. With -p:StudioDesktop=true it becomes a WebView2 desktop app (DesktopHost.cs). Start-Studio.ps1 runs it. Publish-Studio.ps1 publishes the desktop app with a sample pack, notices and an offline handbook.html from export_wiki.py --handbook-only, then zips it. Studio README

CircuitStudio

Plain HTML and JavaScript. index.html with dialogue-model.js simulates dialogue branches, and lessons.html with lessons.js edits lessons. check.cjs and lessons-check.cjs are the DialogueModel and LessonModel suites. Start-CardWorkshop.ps1 builds Content Studio from current sources and opens it in a browser on the canonical pack. Unity's CardForge ▸ Current Card Workshop window (CurrentCardWorkshop.cs) and Open-CardWorkshop.cmd launch it.

Score and Audio

Tools/Score is an offline music renderer: fetch_samples.py downloads pinned samples into Temp, render_score.py and render_circuit.py compose and render the cues and save each arrangement as a *-score.json, and verify_score.py is the Audio suite. Tools/Audio/author_palette.py synthesises the sound effects. Build-PracticeGuide.ps1 makes offline narration placeholders with Kokoro or Windows speech. None of these run in the game. Score README

Documentation

export_wiki.py writes the offline content and code reference and the portable handbook into Builds/Documentation. check_wiki.cjs is the Docs suite, which checks that already-exported output. This wiki is built separately by Tools/Documentation/structure_wiki.py from the pages in Docs/Wiki. Documentation README

Package-Toolkit

Package-Toolkit.ps1 first regenerates the tracked Documentation~/API_INDEX.md from the public declarations under Runtime, so running it can change a committed file. It then stages only the allowed package folders and file types, zips them with a manifest, extracts the ZIP into an isolated consumer and runs Validation~/Run-Validation.ps1 there. Finally it writes Builds/CardForge-Toolkit-<major.minor>.zip and a -validation.json, which also compares the recorded Validation~/unity-import.json hashes.
