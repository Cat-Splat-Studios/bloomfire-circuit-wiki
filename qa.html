How quality is checked

The four kinds of verification code in the repository: portable .NET and script suites, the Unity rehearsal inside a QA player, the editor batch proofs and the two-process network harness. This page covers where each one lives, what it compiles or drives, how it reports, and where QA code reaches into production code.

In 60 seconds

  • Two worlds of checks. Tools/Run-Checks.ps1 runs .NET, Python and Node suites that compile toolkit and game source files by path, without Unity (§02). Everything that needs Unity runs inside a player built with the CIRCUIT_QA define, or inside the Unity editor (§03, §08).
  • One class, ten files. The Circuit rehearsal is CircuitSliceChecks, a partial MonoBehaviour split over ten files in Assets/Tests/Runtime. IsometricSlice.Start installs it when the player was launched with -circuit-verify <dir> (§04).
  • The first failure ends the run. A small runner, Advance over a stack of iterators, drives every stage inline. Require throws on the first false check, Unwind runs the open finally blocks, and the run writes verification.txt and quits with 0 or 1 (§05, §06).
  • Network QA is two real players. ExpeditionHarness installs itself in an EMBERGROVE_QA player started with -expedition-net-verify. A host and a guest play over a real transport and check each other's final state through a shared folder. A detached quickmatch or lobby pair is compared afterwards by Tools/ExpeditionNetworkChecks (§09).
  • QA reaches production in a few known places. These are 21 #if blocks in six runtime files, unguarded flag checks that every player runs, and several hundred string-keyed reflection calls into private members. A rename can break a rehearsal and still compile (§10).

Before you start

Read the Codebase Tour for the assemblies, and the Glossary if a name is new. Have the Unity verification guide open. It owns the entry-point table, the exact command lines and the coverage details that this page only points to. Building the QA players themselves is covered on Builds & Tools.

03The Unity rehearsal

A rehearsal is the real game scene, CircuitJourney.unity, played by code. Virtual keyboard, mouse and gamepad devices drive it, and the run checks the scene's objects and state as it goes. It needs a player built with CIRCUIT_QA (or the editor) and the -circuit-verify <output directory> argument.

sequenceDiagram
  participant P as QA player
  participant S as IsometricSlice
  participant C as CircuitSliceChecks
  participant F as output directory
  P->>S: Start()
  S->>S: LoadCircuit, StartBuildWorld, ShowCircuit(Title)
  S->>C: Install(this), compiled only with the QA define
  C->>C: read -circuit-verify and -circuit-lifecycle
  C->>C: StartCoroutine(Guarded(Rehearse()))

    C->>C: Check(condition, text) to Require
    C->>F: Capture(name) writes name.png
  end
  C->>C: Unwind(stack), Cleanup()
  C->>F: verification.txt
  C->>P: Application.Quit(0 or 1)

One rehearsal run. Install returns immediately without -circuit-verify, so an editor Play Mode session without the flag is unaffected.

  1. Install. The last step of IsometricSlice.Start is CircuitSliceChecks.Install(this), inside #if UNITY_EDITOR || CIRCUIT_QA. Install adds the component to the slice's GameObject, sets RehearsalOwnsFocus on the slice and starts Guarded(Rehearse()). A lifecycle phase gets its own DontDestroyOnLoad host instead (§07).
  2. Take the input. TakeInput sets the input system to IgnoreFocus and adds a virtual keyboard, gamepad and mouse. It then calls OwnInput, which disables every native device for the run and logs which ones in a NOTE line, so a physical mouse or pad cannot become Mouse.current or Gamepad.current mid-run. Cleanup gives them back.
  3. Run the stages. Rehearse() runs some rule checks without waiting a frame (glyph families, menu row availability, every custom Graphic requiring its CanvasRenderer). It then yields the stages in a fixed order, from ArtworkRehearsal through the title, waybook, first steps, deck builder and a played duel to the world fixtures. The order is the source of truth; read Rehearse() in CircuitSliceChecks.cs.
  4. Report and quit. Guarded writes the report and calls Application.Quit(0) on a pass and Quit(1) on a fail (§06).

05The inline runner

Every stage is an IEnumerator that may yield return another stage. Unity runs only the outer coroutine, Guarded. Inside it, Advance walks a Stack<IEnumerator>, so nested stages run inline and any exception reaches one try/catch.

// CircuitSliceChecks.cs: shared with ExpeditionHarness and the editor checks
internal static bool Advance(Stack<IEnumerator> stack, out object yielded)
{
    while (stack.Count > 0)
    {
        var top = stack.Peek();
        if (!top.MoveNext()) { (stack.Pop() as IDisposable)?.Dispose(); continue; }
        object current = top.Current;
        if (current is IEnumerator nested) { stack.Push(nested); continue; }
        yielded = current; return true;
    }
    yielded = null; return false;
}
PieceKindWhat it does
Advanceinternal staticSteps to the next real yield (null, WaitForSecondsRealtime, WaitForEndOfFrame, an AsyncOperation) and hands it to Unity. A yielded IEnumerator is pushed and run at once, so in the code's words "a helper coroutine costs no frame of its own". A finished iterator is disposed as it leaves.
Unwindprivate staticDisposes whatever a stopped run left on the stack, innermost first, so the stages' finally blocks restore their fixtures. A failure during cleanup is added to the failure text.
Requireinternal staticThe single assertion. On false it throws InvalidOperationException with the text, followed by an optional context in brackets. On true it adds "PASS " + text to the list it was given.
CheckinstanceIncrements assertions and calls Require with the observations list and FailureContext. That appends InputDiagnostic (input kind, selection, devices, pointer, focus, frame delta, last press) to every failed check.
Guardedinstance, one per harnessHooks Application.logMessageReceived, loops Advance inside try/catch, then calls Unwind and Cleanup. Any logged Error, Exception or Assert also fails the run. It then writes the build identity and the report and quits.

Three things follow from this design. A check that fails throws, so every later stage is skipped; an assertion total tells you how far a run got, not how much it proved. One deliberately broken build can only test the first guard it trips. And a stage must put back what it changed in a finally, because Unwind is the only cleanup a failed run gets. Tests/README.md owns the procedure built on this ("prove a new guard against the code it guards").

Other users of the runner:

  • CardPresentationBatch in .WorldTable.cs runs Advance and Unwind in its own loop.
  • ExpeditionHarness imports the class as using Rehearsal = EmberGrove.Exploration.CircuitSliceChecks; and uses Rehearsal.Advance, Rehearsal.Require, Rehearsal.WaitUntil, Rehearsal.Render and the reflection helpers. Its Guarded does not call Unwind, counts only logged Exception and Assert messages, and passes no observations list, so its report has no PASS lines.

That shared dependency is why ExpeditionHarness.cs stops the compile with #error when EMBERGROVE_QA is defined without CIRCUIT_QA.

06verification.txt and screenshots

A run leaves one text report and a set of PNG captures in the -circuit-verify directory. A process that exits without writing verification.txt has not passed.

The report

The report starts with PASS or FAIL and a title (Bloomfire circuit rehearsal, or the world-only, palette or lifecycle variant). Next come BuildGuid, AssemblySha256 (the hash of the loaded Assembly-CSharp), Version, GraphicsDeviceType, Assertions and Screenshots. After those are the coverage and fixture-scope paragraphs, every PASS and NOTE observation in order, and finally the failure or "No runtime exceptions observed." A player with no build GUID fails.

The captures

Capture(name) waits for the presentation to settle. It then moves the overlay canvases onto the world camera, renders one frame into a RenderTexture through Render (a render request under URP), and checks that the frame is not blank (LightRange > 100). It writes <name>.png and restores the canvases and camera. Names sort by stage, for example 01-world, 05d-deck-builder-* and palette-02-tasks-<palette>.

The candidate packager reads three identity lines from the report: Tools/Package-Isometric.ps1 requires exactly one BuildGuid, AssemblySha256 and Version line, and each must match the QA player's build-info.json (builds.html §06). Some captures carry their own checks: written: true re-renders the waybook page without the interface and requires ink on it (CheckWrittenPage), and menus-nav-pause-* captures check rendered menu borders.

Why a rehearsal never touches the tester's settings or save

Two pieces of code that ship in every player react to the flag, not only the QA code. ExpeditionApp.PreferenceKey appends .qa.<hash> to every PlayerPrefs key when -circuit-verify or -expedition-net-verify is present, where the hash is taken over the full output path. IsometricSlice.CircuitVerifying suppresses Circuit saves and loads content from StreamingAssets/Content instead of an override. Because the key is a hash of the path, reusing an output directory inherits that directory's earlier preferences, and the guide says to use a fresh path for any run you want to compare.

07Lifecycle phases

-circuit-lifecycle <phase> tests what survives a real scene unload and a real process exit. Each phase is a separate launch of the QA player into the same fresh output directory. Each phase leaves lifecycle-checkpoint.json for the next one, and each writes its own lifecycle-<phase>.txt instead of verification.txt.

  state "unload" as unload
  state "quit-battle" as quitBattle

The four phases and what each passes on. Each later phase first checks that the checkpoint names its predecessor, then that the restored state equals the checkpoint's CircuitSave after CircuitRules.Recover.

  • Saves. LifecycleSaveDirectory resolves to <output>/saves and throws if that path is inside Application.persistentDataPath. IsometricSlice.CircuitStorageRoot picks it up through a CIRCUIT_QA block, so the phases use the production save adapter on isolated files.
  • Surviving a reload. The runner lives on a DontDestroyOnLoad GameObject and is kept in the static lifecycleRunner. When the reloaded scene's IsometricSlice.Start calls Install again, Install rebinds the existing runner to the new slice and returns. LifecycleReloadScene checks that exactly one runner exists.
  • Order is enforced. unload refuses an output directory that already has a save or checkpoint. The procedure (four launches, which reports to read) is in Tests/README.md. What the save format promises is on Saves & Settings.

09The network harness

ExpeditionHarness (namespace EmberGrove.Expedition, two partial files) plays a whole networked match between two independently running QA players over a real transport. Each player writes its own report and capture. Two players that share a parent folder check each other's final public state there; a detached pair is checked afterwards by a separate console tool.

Install. A [RuntimeInitializeOnLoadMethod(AfterSceneLoad)] method reads the arguments. Unlike the Circuit rehearsal, no production code calls it. On Android, NetworkLaunchArguments builds those arguments from the launch intent extra bloomfire.qa (mode:role:run-id:port), using ParseAndroidNetworkLaunch. The editor build's Android preparation checks call CheckAndroidNetworkLaunch to test that parser.

A pair run in the LAN, relay or trusted-room modes. Quickmatch, lobby and the named-room modes add their own steps before the match, where the two players meet. In the trusted modes each player also suspends and resumes once mid-match, and with -expedition-net-faults runs RehearseLostAcknowledgements. At revision 42 a player concedes, so a run always ends.

What each player writes. A player writes these files:

  • verification.txt, titled "Expedition UI rehearsal".
  • network-summary.txt, with commands sent, snapshots observed, final revision and result ID.
  • public-final-state.txt.
  • network-capture.json, the NetworkCapture schema with the public-state hash, protocol versions and fault flags.
  • In the trusted modes, result-id.txt.
  • For the named-room modes, named-room-capture.json, plus automatic-relay-capture.json when the endpoint is the private test preset.
  • Screenshots, and playtest feedback under Feedback/.

A detached client's report says so in its text: its own PASS is not a pair pass. Pair agreement then comes from dotnet run --project Tools/ExpeditionNetworkChecks -c Release -- compare-player-reports, which reads both network-capture.json files and the authority run's saved health response, and accepts only fault-enabled quickmatch or lobby captures (see ExpeditionNetworkChecks § Independent Unity player captures).

Comparing two network runs by assertion count. The match loop in ExpeditionHarness.Network.cs adds three checks for every newly observed revision: the remote projection hides the shuffle state, the opponent's hand and both decks. It adds one check before every submitted command. The total therefore grows with match length. The part that should not change between two runs of the same mode is assertions − 3 × snapshots observed − commands sent, with the last two values taken from that run's network-summary.txt. This rule comes from reading the loop; it is not written down anywhere else.

The device commands for a Windows–Android pair are owned by NETWORKING § Mixed Windows–Android test plan, and the private relay test by NETWORKING § Private QA two-device test. How the transports work is on Networking.
